# 议题 49：`Task.request_cancel()` 请求接口

> 状态：已确认，议题 50—52、61 补充；批量取消令牌待定  
> 确认日期：2026-08-02

## 1. 显式请求方法

`Task::<T>` 提供线程安全的取消请求方法：

```ink
task.request_cancel();
```

方法名称使用 `request_cancel`，而不是 `cancel`。它只表示发出议题 48 的协作式请求，不承诺任务已经停止、将会停止或以某种特殊状态结束。

概念签名为：

```ink
class Task<T: type> {
    func request_cancel();
}
```

## 2. 返回 `void`

`request_cancel()` 返回 `void`，不返回“取消成功”布尔值。调用返回时无法可靠断言：

- 任务是否已经在另一个线程完成；
- 任务是否支持取消；
- 任务将在何时观察请求；
- 任务观察后会返回、抛出还是忽略；
- 已登记的底层 I/O 是否真的能够撤回。

需要知道任务最终结果时，调用方仍须 `await`，或使用所选调度库明确定义的结果接口。

## 3. 幂等且线程安全

多个线程或任务可以并发调用同一任务的 `request_cancel()`。所有调用共同表达单向状态：

```text
not requested → requested
```

必须满足：

- 第一次请求原子地发布请求位；
- 后续重复请求没有额外语言级效果；
- 请求状态不会恢复为未请求；
- 并发请求不重复执行用户代码；
- 请求操作本身不抛异常；
- 请求与任务完成并发发生时不改写已发布终态。

实现可以合并重复的底层通知，但不能因并发调用破坏任务或等待对象状态。

## 4. 对 `created` 任务的行为

对尚未执行的惰性任务请求取消，只预先记录请求，不阻止以后由 `await` 驱动任务：

```ink
var task = operation();

task.request_cancel();
const result = await task;
```

`operation` 仍按照议题 44 开始执行，并可以从第一次用户代码开始观察：

```ink
cancel_requested() == true
```

语言不会跳过函数体、伪造返回值或构造异常。任务也可以忽略预先存在的请求并正常完成。

如果程序只想丢弃一个从未执行的惰性任务，无须请求取消；让该 `created` 任务离开作用域即可清理帧而不执行函数体。

## 5. 对 `pending` 任务的行为

对 `pending` 任务请求取消时，运行时：

1. 设置任务控制状态中的请求位；
2. 如果任务登记在取消感知等待中，通知该等待；
3. 立即从 `request_cancel()` 返回。

该方法不等待任务响应。任务可能继续运行很长时间，甚至永远不查询请求。发出请求的代码不能因此提前销毁任务对象、协程帧或任务仍会访问的存储。

议题 51 规定：请求后仍为 `pending` 的任务不能析构；调用方必须可靠 `await` 到最终状态，或由从一开始就明确取得其稳定存储和生命周期责任的库设施继续管理它。

## 6. 对最终状态任务的行为

如果任务已经发布 `succeeded` 或 `failed`，`request_cancel()` 没有可观察效果：

- 不改变成功结果；
- 不替换 `ExceptionBox`；
- 不重新执行任务；
- 不产生 warning 或异常；
- 不调用已经解除登记的取消通知。

请求和最终状态发布之间发生竞态时，允许请求位最终处于已设置状态，但请求不能追溯改变已经发布的任务结果。

## 7. 不取得或延长所有权

`request_cancel()` 只访问现有 `Task::<T>`，不会复制任务、增加用户可见引用计数或延长任务生命周期：

```ink
func stop(task: Task::<Data*>*) {
    task->request_cancel();
}
```

通过原始指针跨线程请求时，程序员负责保证：

- 指针指向有效且正确对齐的 `Task::<T>`；
- 调用期间任务对象没有被并发销毁；
- 任务控制状态支持目标平台要求的同步；
- 指针访问满足议题 04 的其他前置条件。

线程安全只覆盖有效任务对象内部的请求竞态，不修复悬空指针；违反对象生命周期前置条件仍可能产生 UB。

## 8. 当前任务查询与外部请求对应

议题 48 的：

```ink
cancel_requested() -> bool
```

查询当前正在执行的任务。本议题的：

```ink
other_task.request_cancel();
```

向目标任务设置同一个逻辑请求状态：

```text
target.request_cancel()
    → publish target cancellation-request bit
    → target later calls cancel_requested()
    → observe true
```

查询不清除请求，目标任务不需要持有请求者的对象或回调。

## 9. 与组合等待的关系

议题 46 的 `all_cancel_on_error(...)` 使用与 `request_cancel()` 相同的内部请求协议。当一个输入失败时，组合器向其他尚未结束的输入发布请求，并继续等待全部输入实际结束。

组合器可以使用内部批量路径，编译器不必真的生成逐个公开成员调用；但可观察结果必须与对每个有效未完成任务请求取消一致。

普通 `all(...)` 不调用该协议，也不因某个输入失败而设置请求位。

## 10. 第一版不要求 `CancelToken`

单个 `Task::<T>` 已经是 `[noncopyable]`、具有稳定运行时状态的对象，可以直接保存请求位。为每个单任务请求额外建立取消源、令牌或共享控制块没有必要。

未来以下场景可能需要显式取消令牌：

- 一次请求控制多个不属于同一组合器的任务；
- 把请求能力交给不应获得完整 `Task::<T>*` 的代码；
- 跨库级调度设施或外部 I/O API 传递请求；
- 建立父子请求传播或超时域。

这些令牌必须作为显式标准库对象设计，不能改变 `Task.request_cancel()` 的零额外所有权语义。

## 11. 库管理任务时的取消

议题 52 规定核心语言不定义 `Executor`、`spawn` 或执行器控制句柄。库可以定义自己的后台任务对象和控制 API。

库控制对象如果最终把操作转发为 `Task.request_cancel()`，该部分仍使用本议题的协作式请求语义：只发布请求，不承诺停止，也不把请求改成特殊异常或任务终态。

库对象是否可复制、如何取得所有权、怎样关闭以及如何观察结果，均由库契约确定。库也可以定义与 `Task.request_cancel()` 不同名称的更高层操作，但必须说明其实际保证和成本。

## 12. 成本模型

`request_cancel()` 的最低成本通常是：

- 一次原子设置或原子读改写；
- 请求首次发布时对可选取消感知等待的通知；
- 必要的同步与分支。

无取消请求时不会执行成员方法。请求位通常可以复用议题 48 的任务控制原子字，不要求额外分配。

方法返回不等待目标任务，因此不包含 join 成本。通知取消感知 I/O 的额外成本仅在任务已经登记相关等待时发生。

## 13. LLVM 与运行时实现

该设计不需要修改 LLVM 源码。前端把成员调用降低为 Ink 运行时请求入口或内联原子操作：

```text
Task.request_cancel(task):
    old = atomic_or task.control_flags, CANCEL_REQUESTED
    if bit was newly set:
        notify task.registered_cancel_wait
    return
```

通知登记与任务完成必须通过运行时协议避免 use-after-free 和丢失通知。LLVM 提供的普通原子、控制流和函数调用已经足够，不需要理解取消的协作语义。

## 14. 后续问题

以下内容留给后续议题：

- `cancel_requested()` 的最终核心模块位置；
- 取消感知等待的登记、解除和完成竞态；
- 显式 `CancelToken`、取消域和批量请求；
- 超时如何发布请求；
- 对请求 API 的权限封装；
- freestanding 或无锁原子目标的支持。

议题 50 已确定等待者使用 `await cancel_on_request(task)` 显式把自身收到的请求转发给目标任务，并要求登记、解除与完成竞态无丢失、无悬空访问。

执行器控制句柄与 `spawn` 结果已由议题 52 划归库设计，不再作为核心语言待定项。
