# 议题 51：`Task` 析构状态规则

> 状态：已确认，议题 52、53 补充  
> 确认日期：2026-08-02

## 1. `Task::<T>` 具有确定性清理

`Task::<T>` 是议题 43 确定的 `[noncopyable]` 运行时对象。它拥有或控制：

- 异步函数状态机帧；
- 在调用点保存的参数和捕获状态；
- 任务成功结果或失败 `ExceptionBox`；
- continuation 和取消请求运行时状态；
- 固定的模块版本及兼容销毁入口。

任务对象生命周期结束时必须根据当前状态清理这些资源。该清理属于内建 `Task::<T>` 实现，不允许用户覆盖其状态协议。

## 2. 状态与析构行为

任务析构至少按照以下状态分派：

```text
destroy Task::<T>:
    created   → destroy saved arguments and frame
    succeeded → destroy result storage and frame
    failed    → release ExceptionBox and frame
    pending   → fatal runtime trap
```

`Task::<T>` 没有 `cancelled` 终态，因此不需要取消专用析构分支。

## 3. 销毁 `created` 任务

尚未被驱动的惰性任务可以直接离开作用域：

```ink
func example() {
    var task = operation(make_argument());
} // operation 函数体不执行
```

析构时：

- 不执行异步函数体；
- 销毁调用时保存的实参和捕获状态；
- 释放尚未运行的协程帧存储；
- 解除议题 44 的模块版本固定；
- 解除尚未使用的取消请求和其他运行时状态。

预先调用过 `task.request_cancel()` 不改变该规则。请求位不会迫使任务执行，也不会要求构造特殊结果。

## 4. 销毁成功任务

`succeeded` 任务已经不再执行函数体。析构时：

- 销毁任务保存的只读结果存储；
- 销毁帧中仍由任务持有的状态；
- 释放 continuation 和控制块存储；
- 解除模块版本固定；
- 释放任务自身占用的动态存储。

通过 `Task::<T>*` 取得的原始结果指针不代表任务拥有指针目标。销毁任务只销毁结果槽中的指针值，不自动销毁其指向对象。

## 5. 销毁失败任务

`failed` 任务析构时释放它对 `ExceptionBox` 的内部持有，然后清理帧和模块固定。仍有独立活动等待者持有同一 box 时，box 按议题 43 继续存活；最后一个内部持有释放后才销毁异常载荷。

议题 53 规定核心任务不记录失败是否曾被观察。销毁 `failed` 任务不会打印、调用用户处理器、把 box 重新抛出、启动异常展开或进入 fail-fast；它只执行上述资源清理。

## 6. 禁止销毁 `pending` 任务

`pending` 表示异步函数可能正在运行、挂起或仍被运行时调度设施和 continuation 引用。此时释放任务帧会造成 use-after-free，隐式 detach 又会改变所有权。

因此销毁 `pending` 任务是规范定义的致命运行时错误：

```ink
func example() {
    var task = operation();
    register_external_waiter(&task);

    // 如果外部等待者已经驱动 task 且任务尚未结束：
    return; // 作用域析构 task 时触发 fatal trap
}
```

运行时立即进入不可恢复的 trap/fail-fast 路径，不抛出可捕获异常，也不继续执行尚未完成的普通清理动作。

该行为不能在优化构建中变为静默释放、隐式 detach 或任意 UB。实现可以在终止前输出任务创建位置、当前状态和调试标识；精确诊断格式待定。

## 7. 不在析构时隐式等待

`Task` 析构函数不会自动 join 或阻塞等待任务完成：

- 析构可能发生在不能挂起的普通同步上下文；
- 阻塞 OS 线程会破坏异步调度设施的进展；
- 任务可能等待当前线程或当前作用域释放的资源，形成死锁；
- 隐式等待时间无法从源码看出；
- 析构函数不能执行异步 `await`。

需要完成同步时必须在正常控制流中显式 `await`。

## 8. 请求取消不能代替等待

议题 49 的请求只设置协作式标志。对于已经被其他等待者驱动的任务，必须等待它真正结束：

```ink
register_external_waiter(&task);
task.request_cancel();
await task;
```

只有 `await task` 等待到任务最终结束后，任务才可以安全离开作用域。下面的写法违反任务生命周期规则：

```ink
register_external_waiter(&task);
task.request_cancel();
// task 仍可能 pending
return; // 若析构时仍 pending，则 fatal trap
```

任务可以忽略请求或长时间延迟响应，因此析构不能把“已请求”当作“已完成”。

如果任务从未被任何等待者驱动，它仍是 `created`；此时即使已经调用 `request_cancel()`，离开作用域也按第 3 节安全清理。

## 9. 不在析构时隐式 detach

析构不能把 `pending` 任务自动转交给全局运行时、线程池或其他调度设施。这样做会隐藏：

- 帧和捕获状态的新所有者；
- 结果与异常的观察责任；
- 模块版本固定期限；
- 原始指针目标的生命周期要求；
- 后台调度设施关闭时的行为。

需要长期后台运行的工作必须通过某个显式库 API，从一开始建立独立的稳定存储和生命周期契约；不能由局部任务析构临时补做所有权转移。核心语言不定义该库 API 的名称或句柄类型。

## 10. 编译器诊断

编译器能够从控制流证明局部任务可能以 `pending` 状态离开作用域时，应给出 warning。诊断依据是任务可能已经被驱动且尚未完成，而不是仅仅出现了 `request_cancel()` 调用。

单独对一个从未被驱动的 `created` 任务调用 `request_cancel()` 后离开作用域仍然安全；编译器不应仅凭该调用产生 `pending` 析构 warning。

如果语言规则能静态证明析构点必然为 `pending`，实现可以升级为编译错误；第一版只要求 warning，以免引入完整任务状态流分析。

原始指针别名、跨线程等待和外部调度库通常无法静态证明，运行时致命检查仍是最终防线。

## 11. 并发销毁的前置条件

“任务状态已经最终发布”不自动授权任意线程并发销毁任务。调用方还必须保证：

- 没有线程正在通过原始 `Task::<T>*` 访问任务；
- 没有尚未解除的等待或取消传播登记；
- 任务完成发布与销毁之间存在必要同步；
- 运行时已经完成最终 continuation 的安全交接。

普通 `await` 和议题 45、50 的组合等待必须在返回前提供所需同步并解除自身登记。绕过这些协议，通过悬空或竞态原始指针销毁任务仍违反议题 04 的底层生命周期前置条件，可能产生 UB。

`pending` 状态检查不能把本来存在的数据竞争或悬空指针变成合法访问。

## 12. 异常展开中的任务析构

局部 `Task::<T>` 也可能在普通异常展开中离开作用域：

```ink
async func example() {
    var task = operation();
    await unrelated(); // 这里抛出异常
} // task 若仍为 created，可以清理
```

如果任务仍为 `created` 或已经最终完成，按普通规则清理。如果某种跨线程用法使它仍为 `pending`，析构触发致命 trap；不能因为当前已经在异常展开中就忽略任务生命周期违约。

该 trap 不是第二个可传播异常，不参与 `catch`，也不尝试保留原异常继续展开。

## 13. 库管理的任务

议题 52 允许库为后台任务建立自己的稳定存储和所有权协议。库在回收 `Task::<T>` 存储前同样必须保证任务已经到达最终状态，并解除全部通知与 continuation。

核心语言不规定库如何接收工作、返回何种控制对象或者怎样关闭。等待、请求取消后等待、拒绝关闭、批量回收等均由库契约选择；任何库都不得直接释放仍在运行的任务帧。

## 14. 成本模型

任务析构本来就必须读取或已知当前状态，才能选择结果、异常和帧的清理路径。`pending` 致命分支不要求增加任务对象字段或独立分配。

编译器能够静态知道任务仍为 `created`，或者知道控制流刚完成一次可靠 `await` 时，可以直接生成对应清理并消除动态状态分派。无法证明时执行一次状态读取和分支。

正确程序不承担隐式 join、detach、引用计数或取消等待成本。

议题 53 进一步排除 observation bit、观察计数和析构时的未观察失败检查，因此成功和失败 `await` 都不需要为了诊断而写回任务状态。

## 15. LLVM 与运行时实现

该设计不需要修改 LLVM 源码。前端为 `Task::<T>` 清理生成普通状态分派：

```text
switch atomic_load(task.state):
    created   → destroy_saved_arguments_and_frame
    succeeded → destroy_result_and_frame
    failed    → release_exception_box_and_frame
    pending   → runtime_fatal_pending_task_destruction
```

异常路径使用普通 cleanup/funclet 运行相同状态分派。运行时终止入口、原子状态和模块固定都可以用 LLVM 现有控制流、原子操作和平台异常清理表达，不需要 LLVM 理解任务生命周期。
