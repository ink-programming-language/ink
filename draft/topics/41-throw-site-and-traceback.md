# 议题 41：抛出位置与可配置 traceback

> 状态：已确认，议题 42、43 与 Parser 议题 27 补充，精确诊断 ABI 待定
> 确认日期：2026-08-02

## 1. 抛出位置与完整 traceback 分离

Ink 把异常诊断分成两个层次：

- 每个新异常记录始终保存一个轻量 `throw_site`；
- 完整 traceback 只在构建配置和当前运行时配置允许时捕获。

这样 Release 构建可以只保留异常的直接来源，而 Debug、测试或诊断运行可以取得完整调用链。

两者都是诊断元数据，不参与异常类型匹配、对象布局、原因链选择或程序控制流语义。

## 2. 每个新异常始终记录抛出位置

编译器为每个产生新异常的 `throw` 源码位置生成静态 `ThrowSite` 描述，并在创建 `ExceptionRecord` 时保存对它的引用：

```ink
if (!file.exists()) {
    throw FileNotFound { path }; // 独立 throw site
}
```

逻辑记录至少包含：

```text
ExceptionRecord {
    ...
    throw_site
    optional traceback_storage
    payload
}
```

保存 `throw_site` 不遍历调用栈、不分配动态数组，异常记录中的常规成本约为一个位置描述引用。

## 3. `ThrowSite` 描述

`ThrowSite` 在语义上能够识别：

- 产生异常的模块及模块版本；
- 模块内抛出位置或指令偏移；
- 可用时的完全限定函数名称；
- 可用时的源文件、行号和列号。

构建系统可以裁剪绝对源路径、函数符号和行列映射，但必须保留足以让运行时区分抛出位置的静态描述。缺少调试符号时，报告器仍可以输出模块版本和位置偏移或等价目标信息。

抛出位置不是跨重新编译稳定的持久化 ID。源码编辑、优化、链接和热更新都可能改变其模块内位置。

## 4. 哪些操作产生新抛出位置

以下操作创建新异常记录，因此记录当前 `throw` 位置：

- 直接构造并抛出异常；
- 从命名异常变量复制并抛出；
- 在处理器中抛出一个新的包装异常；
- 使用议题 40 的 `throw NewError { ... } from error;`。

被调用函数内部抛出的异常记录该函数自己的 `throw` 位置，而不是调用表达式的位置。异常从多少层普通函数传播都不会改变原始 `throw_site`。

## 5. 完整 traceback 是可配置诊断

完整 traceback 捕获能力由构建配置决定。包含该能力的程序还可以通过运行时诊断配置决定当前是否捕获以及最多保留多少帧。

语义上至少存在：

```text
full traceback disabled
full traceback enabled with a frame limit
```

构建时已经裁掉完整捕获能力的程序不能仅通过运行时开关重新启用它。运行时配置变化只影响之后创建的新异常记录，不追溯填充或删除已经存在的记录。

具体配置文件、命令行、环境变量和程序化 API 留给运行时配置议题，不属于异常语法。

## 6. 捕获时机

启用完整 traceback 时，运行时在新异常载荷完成构造、异常开始搜索处理器之前捕获当前机器调用栈：

```text
construct exception payload
    → save throw_site
    → capture raw frames if enabled
    → begin handler search and unwind
```

这样被异常展开移除的调用帧仍然可以进入 traceback。捕获过程只发生在真正的异常路径，不给尚未抛出异常的普通调用增加逐调用记录操作。

traceback 保存优化后机器栈可恢复的原始帧信息，不在抛出点立即执行完整符号化。

## 7. 原始帧与延迟符号化

逻辑 `TraceFrame` 至少保存能够安全识别代码位置的信息：

```text
TraceFrame {
    module_version
    instruction_offset_or_address
}
```

运行时在显示或显式请求时，才尝试把帧解析为函数名称、源文件和行列号。这样真正抛出但最终被程序处理的异常不必预先支付字符串格式化和符号查找成本。

实现可以对同一模块版本共享符号目录和解析缓存。缓存键必须包含模块版本，不能把热更新后复用的地址或偏移解析成错误版本的函数。

## 8. 捕获失败只能降级诊断

完整 traceback 是尽力而为的诊断功能。以下情况都不能阻止语言异常继续传播：

- traceback 存储分配失败；
- 栈展开器无法继续恢复某一帧；
- 达到配置的最大帧数；
- 遇到没有兼容展开信息的外部代码；
- 紧急异常记录没有空间保存完整栈。

运行时可以返回空 traceback 或标记为截断，但始终保留轻量 `throw_site`。它不能为了报告 traceback 失败而递归抛出另一个普通异常。

诊断 API 应能区分“完整捕获被关闭”“捕获结果为空”和“结果被截断”；精确状态枚举留给核心诊断 ABI 确定。

## 9. `ExceptionView` 查询

`core.ExceptionView` 提供两个只读、`[nothrow]` 查询：

```ink
[nothrow]
func throw_site() -> ThrowSiteView;

[nothrow]
func traceback() -> TracebackView;
```

`ThrowSiteView` 始终有效。`TracebackView` 是非拥有安全切片式视图，可以为空，并能够报告帧数和是否截断；每个帧是只读 `TraceFrameView`。

这些视图及其返回的名称或源位置字符串都继承当前 `ExceptionView` 的短期不逃逸限制。它们不能存入全局、长期字段、异步任务或其他线程，也不能在异常记录释放后继续使用。

原始帧表示、迭代器和符号化函数的精确核心库 API 留给诊断 ABI，但不得允许通过这些视图修改异常记录或模块元数据。

## 10. `throw;` 不重写 traceback

重新抛出复用同一个 `ExceptionRecord`：

```ink
catch IoError as error {
    log(error.message());
    throw;
}
```

`throw;`：

- 保留最初创建记录时的 `throw_site`；
- 保留已经捕获的 traceback；
- 不追加重新抛出处理器作为新起点；
- 不因为当前 traceback 配置变化而重新捕获。

调试器可以把重新抛出作为运行时事件观察，但该位置不伪装成异常的原始来源。

## 11. 新包装异常和原因各自保存诊断

显式包装创建新记录，因此捕获新的位置和可选 traceback：

```ink
catch ParseError as error {
    throw ConfigurationError {
        message: "invalid configuration",
    } from error;
}
```

概念诊断结构为：

```text
ConfigurationError
    throw_site  = 包装位置
    traceback   = 包装位置的调用链
    cause       = ParseError
        throw_site = 原始解析失败位置
        traceback  = 原始解析失败调用链
```

新异常不会覆盖、拼接或重新解释原因异常的 traceback。未捕获报告器可以按原因链逐段显示它们。

## 12. 优化与平台差异

完整 traceback 反映目标平台和优化后机器代码能够恢复的调用链：

- 内联调用可能只在存在相应调试信息时恢复为逻辑内联帧；
- 尾调用消除可能使某些源码调用不再具有独立机器帧；
- 省略帧指针不会自动禁止捕获，但目标必须提供可用展开信息；
- 外部汇编、JIT 或不兼容 ABI 代码可能截断结果；
- 函数名称和源行信息取决于符号与调试数据裁剪。

因此程序可以显示和记录 traceback，但不能把精确帧数量、函数文本或源路径当作跨平台、跨优化级别的可移植业务语义。

## 13. 热更新与模块元数据

原始绝对地址可能在模块卸载后失效或被新映射复用。运行时必须采用以下任一安全方案：

- 在 traceback 生命周期内固定对应模块映射和符号元数据；
- 捕获时把地址规范化为模块版本加相对偏移，并保留独立符号目录；
- 使用能提供同等版本隔离的运行时句柄。

只为延迟符号化保留的模块版本元数据不必包含可执行权限，也不一定阻止代码映射卸载；但实现不能把旧帧交给同地址的新模块版本解释。

异常类描述符、销毁入口和原因记录原本需要的模块固定仍遵守议题 17、35、36 和 40，不能因为 traceback 使用独立符号目录而提前释放。

## 14. 未捕获报告与敏感信息

议题 42 的未捕获异常报告器至少输出最外层异常类型和 `throw_site`。配置允许时，可以继续输出：

- 完整或截断 traceback；
- 原因链中每个异常的抛出位置和 traceback；
- 可用函数符号、源文件和行列号。

绝对文件路径、原始地址、函数符号和业务异常内容可能包含敏感信息。生产运行时可以按照诊断策略隐藏路径前缀、关闭原始地址输出、裁剪符号或限制帧数；这些输出策略不删除异常记录自身的语言语义。

符号化或格式化失败不能再次抛出普通异常。报告器必须回退到更少信息并继续执行未捕获异常的终止策略。

进程级 fail-fast 不保证为了获得更多帧而继续语言级栈展开；完整 traceback 必须已经在议题 41 规定的新异常创建阶段捕获。未捕获观察钩子只能借用现有诊断数据，不能要求恢复执行后重新采集。

## 15. 成本模型

没有异常发生时：

- 不遍历调用栈；
- 不分配 traceback 存储；
- 不执行符号查找或格式化；
- 仍存在静态 `ThrowSite` 描述和已有异常展开元数据的代码尺寸成本。

真正抛出时始终写入一个轻量抛出位置引用。启用完整捕获时，额外成本通常与实际检查的帧数线性相关，并可能需要存储分配；延迟符号化的成本只在显示或显式查询符号时发生。

`TracebackView` 查询本身只是借用已保存数据，不分配、不复制帧，也不增加引用计数。

议题 43 的 `ExceptionBox` 长期保留生产者侧 `throw_site`、traceback 和原因链。每次失败 `await` 的位置和消费者侧传播上下文保存在该等待者自己的活动展开记录中，不写回共享 box。重复等待因此共享原始诊断载荷，但可以分别报告各自的等待位置。

## 16. LLVM 与运行时实现

该设计不需要修改 LLVM 源码：

- Ink 前端为每个新异常 `throw` 生成静态位置描述并传给异常运行时；
- LLVM 已有展开表和目标异常 ABI 提供恢复机器帧所需的基础数据；
- Itanium 风格目标可以使用兼容展开器或系统 unwind API 捕获地址；
- Windows 目标可以使用相应虚拟展开能力；
- 符号化使用目标已有调试信息、符号表或 Ink 生成的紧凑位置表。

运行时必须在开始破坏性展开前完成需要的原始帧捕获。LLVM 不需要理解 `ThrowSiteView`、`TracebackView` 或原因链的语言语义。

## 17. 后续问题

以下内容仍留给后续议题或核心诊断 ABI：

- 完整 traceback 构建选项、运行时配置和默认值；
- `ThrowSiteView`、`TracebackView` 与 `TraceFrameView` 的精确二进制布局；
- traceback 状态枚举、帧迭代和符号化 API；
- 符号目录缓存、版本保留和隐私裁剪策略；
- 异步边界链和消费者侧等待位置的精确查询与显示 API；
- freestanding、内核及无系统展开器目标的降级方案；
- 外部异常和外部栈帧的互操作规则。
