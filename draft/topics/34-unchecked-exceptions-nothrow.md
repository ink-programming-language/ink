# 议题 34：未检查异常、展开与 `[nothrow]`

> 状态：已确认，议题 35—48、52、58 与 Parser 议题 27—29 补充
> 确认日期：2026-08-02

## 1. 异常不进入普通函数签名

Ink 的普通函数、方法和构造函数默认都可能抛出异常，但不在声明中列出是否抛出或可能抛出的异常类型：

```ink
func load_config(path: StringView) -> Config {
    const file = File.open(path);
    return parse_config(file);
}
```

Ink 不提供 `throws` 声明，也不提供 Java 式受检查异常列表。底层函数以后新增一种异常，不要求所有间接调用者修改函数签名。

异常能力不改变普通参数和返回类型的源码签名。`[nothrow]` 同样不进入普通重载签名或函数值类型；它是附着在可调用声明上的独立行为契约。

## 2. 调用点不标记传播

调用一个可能抛出异常的函数时，不写前缀 `try` 或后缀 `?`：

```ink
const file = File.open("data.txt");
const config = parse_config(file);
```

调用成功时产生普通结果；调用抛出时，控制流自动离开当前表达式和作用域，执行清理并继续向上查找处理器。

此前草案中用于异常传播的：

```ink
try function()
function()?
```

均不属于最终 Ink 语法。`Optional<T>` 继续通过议题 33 的 `if match` 或 `match` 显式处理，也不使用异常传播语法解包。

## 3. `throw`

函数使用 `throw` 产生异常：

```ink
if !file.exists() {
    throw FileNotFound { path };
}
```

`throw` 后当前控制流不再正常继续。异常值按照议题 36 保存在运行时拥有的异常记录中，直到处理或未捕获异常路径结束。直接构造表达式原地构造载荷；从命名变量抛出时按值复制。

Parser 议题 27 确认三个语句形态：`throw expression;` 创建新异常，`throw expression from identifier;` 显式连接当前异常原因，`throw;` 重新传播当前记录。三者都必须写出结尾分号，并且都不是表达式。

议题 40 允许在处理器内使用 `throw NewError { ... } from error;` 显式建立新异常到当前异常的原因链。普通 `throw` 不自动保存当前异常。

原始指针 UB、PDB、普通 trap、`abort`、硬件故障和进程终止不自动转换成可捕获异常。只有语言或库明确执行的异常路径参与本议题的展开机制。

## 4. `try`/`catch` 只用于处理区域

`try` 不是函数调用前缀，只用于建立具有处理器的语句块：

```ink
try {
    const config = load_config("config.json");
    run(config);
} catch IoError as error {
    log(error);
} catch ParseError as error {
    report(error);
}
```

`catch Type as name` 按异常动态类型匹配并在处理器作用域中绑定异常值。Parser 议题 28 还允许省略不需要的类型化绑定：`catch Type { ... }`。议题 35 规定合法异常类、异常接口、匹配顺序和绑定类型；`as` 的该用途由本议题确认，不表示类型转换。

每个 `try` 至少需要一个处理器。`catch { ... }` 和 `catch as name { ... }` 是 catch-all，最多出现一次且必须位于处理器列表最后；这一顺序错误不能降级为不可达 warning。

不需要 Java 式“捕获或声明”。没有匹配当前异常的 `catch` 时，异常继续向调用者传播。

Ink 不提供 `finally`；无论正常离开、提前返回还是异常展开都必须执行的清理由 RAII 和 `defer` 表达。

异常类和异常接口匹配由议题 35 规定。议题 37 规定 `catch {}`、`catch as error` 和 `throw;`；议题 39 确认不提供异常过滤器或多类型捕获。

## 5. 栈展开和 RAII

异常传播是结构化的非正常控制流。离开每个作用域时，编译器必须按照议题 03 执行：

- 已成功初始化局部对象的逆序析构；
- 已注册 `defer` 的后进先出清理；
- 部分构造对象中已完成子对象的逆序清理；
- 当前活动枚举载荷的清理。

尚未完成初始化的对象没有生命周期，不调用其析构函数。异常被某个处理器捕获后，从该处理器开始恢复普通控制流；已经展开离开的作用域不会复原。

## 6. 不可复制返回值和构造失败

可能抛出异常不要求把成功值包装进临时 `Result<T, E>`。编译器继续使用议题 02 和 06 的最终目标存储：

```ink
const file = File.open("data.txt");
```

概念调用 ABI 可以提供：

```text
success destination: File storage
exception continuation: native unwind edge
```

成功时 `File` 直接构造在 `file` 的最终存储中；失败时该存储保持未初始化，只清理由调用过程已经完成的内部状态。这不是移动，也不要求 `File` 可复制。

构造函数在完成部分字段后抛出时，只清理已经初始化的字段；完整对象自身的析构函数不运行。

## 7. `[nothrow]` 是显式公开契约

需要保证异常不能逃逸的函数使用无参数内建属性 `[nothrow]`：

```ink
[nothrow]
func hash(data: const byte[]) -> u64 {
    // ...
}
```

`[nothrow]`：

- 只能附着于可调用声明；
- 是公开 API 和跨模块直接调用的行为契约，但不进入函数类型、重载身份、名称修饰或普通调用约定身份；
- 进入编译期反射、动态函数描述符和 API 摘要；
- 映射为后端的不展开保证，例如 LLVM `nounwind`；
- 不能被实现、覆盖方法、装饰器或热更新版本削弱。

Parser 议题 29 因此不提供 `[nothrow] func(...)` 函数类型。属性列表保存在声明外层，普通函数值类型只记录同步或异步种类、参数和结果等自身类型结构。

析构函数、`defer` 清理和议题 06 的 `implicit` 构造函数隐式满足 `[nothrow]`，不要求重复书写属性。

## 8. `[nothrow]` 的静态检查

`[nothrow]` 函数只有在编译器能证明异常不会离开函数时才合法。通常它可以：

- 调用其他 `[nothrow]` 函数；
- 执行不产生语言异常的内建操作；
- 调用普通函数，但必须在函数内部以 catch-all 处理可能异常；
- 在完全受本地处理器覆盖的区域内部产生并捕获异常。

它不能让普通函数调用、`throw` 或议题 37 的 `throw;` 沿调用边逃逸。只捕获若干具体类型不足以证明捕获了未来新增的异常；跨模块 `nothrow` 证明需要使用 `catch {}` 或 `catch as name` 覆盖全部异常，并保证该处理器自身不会重新抛出或产生可逃逸异常。

普通 `func(...)` 函数值不记录来源声明是否具有 `[nothrow]`。调用一个不能静态确定目标的函数值时必须按“可能抛出”处理；位于 `[nothrow]` 函数内时，该调用必须被 catch-all 覆盖：

```ink
[nothrow]
func invoke(callback: func()) {
    try {
        callback();
    } catch {
        return;
    }
}
```

如果编译器能够从直接声明或其他规范允许的证明确定目标具有 `[nothrow]`，则不需要插入无意义的处理器。不能仅凭当前函数体“看起来没有 throw”推断跨模块永久保证。

编译器发现可能逃逸的路径时必须报错，不能把它降级为 warning，也不能通过假设“当前被调用实现没有 `throw`”接受代码。

如果运行时因为 ABI 破坏、外部代码错误或其他无法静态验证的情况观察到异常越过 `[nothrow]` 边界，程序立即终止，不能继续展开到调用者。

## 9. 函数指针、虚函数和接口

Ink 不存在“要求 `[nothrow]` 的函数指针类型”。参数和结果等类型结构相同的函数可以赋给同一个普通 `func(...)` 位置；赋值后，间接调用按可能抛出处理。需要在高阶 API 中保留不抛出保证时，必须由未来独立的函数效果或受约束接口设计明确表达，不能把声明属性暗中塞进普通函数类型。

虚方法或接口方法标记 `[nothrow]` 时：

- 所有类覆盖实现必须保持 `[nothrow]`；
- 接口默认实现必须保持 `[nothrow]`；
- 接口 thunk、虚槽和反射适配器不能让异常逃逸；
- 违反兼容性在编译期报错。

未标记方法的覆盖实现可以新增或改变异常行为，不改变方法签名或槽位 ABI。

## 10. 装饰器

装饰器应用在普通函数上时，可以插入可能抛出异常的调用；异常按照普通规则传播。

装饰器应用在 `[nothrow]` 函数上时，展开后的完整函数体必须重新通过 `[nothrow]` 检查。生成代码只能调用 `[nothrow]` 操作，或者在内部捕获全部异常。

议题 58 的 `async decorator` 属于异步任务执行体。应用于 `[nothrow] async func` 时，前置代码、普通 `await`、特殊 `await function(...)`、后置代码、析构和 `defer` 组成的完整状态机都必须通过本议题检查。未捕获异常不能仅因为来自装饰器就进入任务的 `ExceptionBox`；那仍会违反 `[nothrow]` 公开保证。

热更新不能把一个已发布的 `[nothrow]` 入口替换成可能让异常逃逸的实现。

## 11. FFI、线程和异步边界

Ink 异常不能未经适配穿过不知道 Ink 异常 ABI 的 C 或其他外部 ABI 边界。导出给这类 ABI 的函数必须：

- 标记 `[nothrow]`；或者
- 在导出包装器内捕获全部异常并转换成外部错误码、状态对象或回调。

外部回调进入 Ink 时同样不能假定外部异常与 Ink 异常兼容。

异常不能直接从一个线程展开到另一个线程。议题 42 规定未捕获异常到达普通 OS 线程入口时报告诊断并终止整个进程；需要隔离线程失败的程序必须在线程入口显式捕获。

议题 43 规定异步任务在内部任务边界捕获异常，并由只读、共享的 `ExceptionBox` 保存。任务失败本身不立即触发普通线程的 fail-fast；对失败任务执行 `await` 时，从等待点重新进入普通未检查异常传播。

议题 44 规定普通异步调用只创建惰性任务。实参求值、任务帧构造等创建期异常同步传播；异步函数体只有在第一次直接 `await`、议题 45 的 `await all(...)`，或库设施通过底层任务驱动协议接管后才运行，函数体异常随后进入任务失败状态。`Task<T>` 不提供公开的 `start()`。

议题 45、46 规定组合等待不能在仍有输入任务运行时把失败传播出组合边界。普通 `all` 等待全部输入自然结束；`all_cancel_on_error` 在首个失败后请求取消其他未完成输入，但仍等待它们真正结束。议题 47 规定全部结束后按源码参数顺序选择第一个失败，从组合等待点重新进入普通异常展开。

议题 48 规定取消请求本身不是异常，不触发栈展开，也不增加内建 `CancellationError`。任务可以在观察请求后自行抛出业务异常；该异常随后完全按照本议题的普通未检查异常规则传播。

## 12. `Optional`、`Result` 与异常的定位

三种机制表达不同语义：

- `Optional<T>`：正常的“可能不存在”，调用者通常就地分支处理；
- 标准库 `Result<T, E>`：需要作为普通值保存、排队、组合或显式传递的成功/失败状态；
- 异常：需要跨多层调用自动传播的非局部失败。

`Result<T, E>` 仍是议题 32 定义的普通标准库枚举，不取代异常展开，也不让普通函数签名获得受检查错误列表。

## 13. 反射和动态调用

函数反射描述符记录声明是否具有 `[nothrow]`。没有该属性的函数一律按可能抛出处理，反射适配器必须允许异常沿正常 Ink 展开路径传播。

动态反射 API 自身发现合法但不匹配的类型、参数、访问权限或模块版本时，抛出结构化反射异常，不产生 UB。

跨不支持 Ink 异常的插件 ABI 调用时必须使用第 11 节的边界包装，不能让反射适配器把异常直接交给未知调用约定。

## 14. 优化和热更新

为了允许底层实现新增异常而不修改间接调用者，编译器必须把每个非 `[nothrow]` 的跨模块和可热更新调用视为可能展开，即使当前函数体中没有 `throw`。

编译器可以在同一固定模块版本内证明某次调用不会抛出并局部优化清理边，但不能把该推断发布成跨模块永久契约。只有源码中的 `[nothrow]` 才允许调用者长期省略展开路径。

给已经发布的普通函数新增异常不改变函数类型；给函数新增 `[nothrow]` 是加强声明保证，也不改变函数类型或符号身份。删除已发布的 `[nothrow]` 或让新实现违反它仍属于二进制/API 契约不兼容更新，因为直接调用者可能已经依据该属性省略展开边；实现和热更新系统必须拒绝这种削弱。

异常类型的动态身份遵守议题 22 的完全限定字符串名称规则。描述符指针和哈希只能作为当前加载代次缓存；异常类型重命名等于删除旧类型并创建新类型。

## 15. LLVM 实现

Ink 可以只使用 LLVM 已有异常处理 IR 和目标后端支持，不需要修改 LLVM 源码：

- 普通可能展开调用使用 LLVM 允许展开的调用或 `invoke`；
- 需要清理或捕获的控制流使用 landing pad、personality function 或 Windows funclet 模型；
- `[nothrow]` 入口使用 `nounwind`；
- Windows 目标使用 LLVM 的 Windows EH/funclet 降低；
- 采用 Itanium 风格 EH ABI 的目标使用相应 personality 和展开表；
- 其他目标只有在后端或 Ink 运行时提供兼容展开方案时才启用异常。

正常成功路径通常不执行逐调用错误码分支，但会产生展开表、清理 landing pad 和相应代码尺寸。真正抛出异常时需要搜索处理器并逐层执行清理，成本明显高于普通返回。

## 16. 未捕获异常

异常到达当前执行入口仍没有处理器时不能恢复正常控制流。运行时必须进入明确的未捕获异常处理路径，至少能够报告异常类型和议题 41 的抛出位置，并终止相应执行域；存在原因链或已捕获 traceback 时可以输出进一步诊断。

议题 42 规定普通 `main` 和普通 OS 线程入口采用进程级 fail-fast，并允许不可恢复的 `[nothrow]` 观察钩子。议题 43 规定任务边界把异常保存为失败终态；失败的 `await` 若最终仍逃出 `main`、普通线程或 `[nothrow]` 边界，再进入相同的进程级 fail-fast。
