# 议题 17：模块生命周期、装饰器注册与热更新

> 状态：已确认，议题 18、22、34、36、42—45、55、58、61 与 Module 议题 03 补充  
> 确认日期：2026-08-01

## 1. 生命周期属于模块版本

`module_load` 和 `module_unload` 针对一个具体的模块版本执行，而不是针对每条 `import`、每次函数调用或每个对象实例执行。

- 同一个模块版本被多个模块导入时，只加载一次；
- `module_load` 在该版本对外公开之前执行；
- `module_unload` 在该版本不再接收新调用，且已有调用全部结束之后执行；
- 热更新产生新的模块版本，因此新旧版本各自拥有独立的生命周期和运行时状态。

这些钩子由 Ink 运行时或 Ink 生成的启动代码显式调度，不实现为操作系统动态加载器锁中的隐式回调。

## 2. 普通程序启动与退出

普通程序启动顺序为：

```text
加载并重定位程序
    → 初始化 Ink 运行时
    → 按依赖顺序初始化模块全局对象
    → 调用模块的 module_load
    → 公开模块入口
    → 调用 main
```

被依赖模块先于依赖者完成加载。`main` 开始执行时，正常参与启动的模块都已经完成 `module_load`。

正常退出顺序为：

```text
main 返回
    → 停止产生新的模块调用
    → 按依赖逆序调用 module_unload
    → 析构模块全局对象
    → 结束 Ink 运行时
```

`module_unload` 执行时，本模块的全局对象以及它所依赖模块的全局对象仍然有效。

## 3. 动态加载与卸载

动态模块按以下顺序加载：

```text
映射模块
    → 重定位、目标与 ABI 检查
    → 加载依赖
    → 初始化模块全局对象
    → module_load
    → 对其他线程公开模块句柄与入口
```

因此，其他线程不能观察到只完成了一部分初始化的模块。

动态卸载顺序为：

```text
撤销模块的公开状态
    → 禁止产生新的模块调用
    → 等待正在执行的调用离开该模块版本
    → module_unload
    → 析构模块全局对象
    → 卸载代码和数据
```

如果无法证明不存在仍会进入该版本的函数指针、回调或其他入口，运行时不得卸载其代码。

## 4. 热更新事务

热更新不能直接在正在使用的旧版本上执行加载或卸载钩子。运行时必须先准备完整的新版本，再以事务方式切换：

```text
加载新版本到暂存区
    → 检查目标、ABI 和依赖
    → 初始化新版本全局状态
    → 执行新版本 module_load（暂存事务）
    → 原子提交函数实现槽和注册表
    → 禁止新调用进入旧版本
    → 等待旧版本调用结束
    → 执行旧版本 module_unload
    → 析构并卸载旧版本
```

原子提交之后：

- 新调用进入新版本；
- 已经进入旧版本的调用可以继续完成；
- 函数稳定入口、装饰器生成的注册项和其他加载器管理状态属于同一次提交；
- 不允许出现函数已经更新但注册表仍指向旧状态的中间可见阶段。

如果新版本在提交前加载失败，运行时放弃新版本并继续使用旧版本。已经成功建立的新版本局部状态必须按逆序回滚，加载器管理的暂存注册不得变成全局可见状态。

## 5. 装饰器生命周期块

函数装饰器除了生成函数调用前后的运行时代码，还可以生成与所在模块版本关联的 `module_load` 和 `module_unload` 生命周期块。

```ink
decorator route(function, path: comptime string) {
    module_load(load) {
        load.register(
            registry: RouteRegistry,
            key: path,
            value: Route(path, function.entry),
        );
    }

    return function(...);
}
```

生命周期块仍在运行时执行，但每个模块版本只执行一次；它们不是函数拦截路径的一部分。普通函数调用只执行装饰器围绕 `function(...)` 生成的代码。

`function.entry` 表示被装饰函数的热更新稳定入口，而不是当前版本原始函数体的地址。源码和生成代码不能让原始函数体地址逃逸。

议题 58 规定异步目标的 `function.entry` 是稳定任务构造入口。调用该入口只建立完整装饰后的惰性任务，不直接运行异步装饰器、原始函数体或首次 resume。装饰器生成的生命周期块仍在模块版本加载与卸载时运行，不等待某个异步任务开始。

本议题只确认装饰器可以生成生命周期块。普通源码是否可以直接声明模块生命周期块，留给模块系统议题决定。

## 6. 事务式注册

路由、RPC、测试发现、事件订阅等注册行为必须优先使用加载上下文提供的事务式注册接口，而不是在 `module_load` 中直接修改进程全局容器。

`load.register` 具有以下语义：

- 注册首先进入当前模块版本的暂存事务；
- 注册项带有不可伪造的模块版本所有权；
- 热更新提交时，注册项与函数实现槽一起原子发布；
- 卸载时，运行时只移除属于目标旧版本的注册项；
- 删除旧版本注册项不能删除同一逻辑注册的新版本；
- 加载失败时，暂存注册自动丢弃。

注册表使用自身的语义字符串键，例如路由路径和请求方法。注册项仍带有不可伪造的模块版本所有权，因此旧版本卸载时只能删除旧版本拥有的记录，不能误删相同键的新版本记录。

Ink 不为源码声明生成跨重命名稳定的注册 ID。需要以声明名称注册时，使用议题 22 定义的完全限定名称；重命名按照删除旧项并创建新项处理。

对于完全由 `load.register` 管理的注册，装饰器通常不需要编写对应的 `module_unload`。运行时按照模块版本所有权自动撤销它们。

## 7. `module_unload` 的用途

`module_unload` 用于释放 `module_load` 真正取得、且无法由加载上下文自动管理的运行时资源，例如：

- 后台线程或库级异步任务；
- 设备、窗口系统或操作系统资源；
- 外部服务连接；
- 用户自定义注册系统中的令牌。

这类资源必须属于具体模块版本。卸载钩子不能通过普通注册键删除可能已经属于新版本的状态，而应使用版本所有权或加载时取得的精确令牌。

加载过程中如果 `module_load` 或后续步骤抛出异常，加载器必须在模块边界捕获它，并把尚未提交的新版本视为加载失败；已经完成的加载动作按逆序清理。钩子之间传递版本状态的语法、卸载清理的异常策略以及哪些副作用能够自动回滚，留给模块状态议题确定。

议题 42 规定 `module_unload` 和加载失败回滚清理属于致命不抛出边界。编译器能够证明异常可能逃逸时必须报错；运行时仍观察到异常越界时立即进入进程级 fail-fast，不尝试继续其他卸载或回滚步骤。

## 8. 并发与可见性

模块公开、热更新提交以及注册表切换必须形成发布同步点：看到新函数实现的线程也必须看到该版本在 `module_load` 中完成初始化的状态。

停止旧版本的新调用之后，运行时必须等待该版本的活动调用计数、epoch、hazard pointer 或等价安全机制到达静止状态，才能执行 `module_unload` 和卸载代码。

议题 36 定义的活动异常记录也属于模块版本的活动使用者。只要异常仍在展开、处理或等待重新抛出，运行时就必须固定其异常描述符、异常接口表和销毁代码；旧版本不能在这些记录释放前执行最终代码卸载。

议题 43 的失败任务 `ExceptionBox` 也是模块版本的活动使用者。即使产生异常的异步函数已经结束，只要失败任务状态或任一等待者仍持有 box，旧模块版本的异常载荷布局、描述符、诊断元数据和销毁代码就不能卸载。

议题 44 的惰性任务在创建时就固定异步函数入口和帧 ABI。尚未被等待或组合等待驱动的任务同样属于旧模块版本的活动使用者；热更新后再驱动该任务仍执行创建时绑定的旧版本，直到任务帧释放才能解除固定。议题 45 的 `all` 在其全部输入任务结束前持续保持相应任务帧和模块版本有效。

议题 55 的异步虚调用在任务创建时选择覆盖。运行时必须在调用版本专用任务构造 thunk 之前取得对应模块版本固定；构造成功后由任务持续持有，构造失败则释放。旧版本卸载必须等待这类任务释放其构造入口、coroutine frame、resume、destroy、异常边界和相关元数据，不能只等待最初的虚槽调用返回。

议题 58 的异步装饰器与最终函数体属于同一个具体 coroutine frame 和模块版本固定。旧任务未完全销毁前，运行时不能卸载其装饰器生成代码、跨暂停局部状态的析构入口或展开来源元数据。

本规范只规定可观察语义，不强制某一种静止状态实现。

模块之间、模块内部以及堆叠装饰器生成的生命周期钩子顺序由 [`18-module-lifecycle-hook-order.md`](./18-module-lifecycle-hook-order.md) 规定。

## 9. 非正常终止

以下情况不保证调用 `module_unload`：

- 进程崩溃；
- `abort` 或等价立即终止操作；
- 操作系统强制结束进程；
- 硬件失效或运行环境被直接销毁。
- 议题 42 的未捕获异常或不抛出边界违约导致的进程级 fail-fast。

程序不能依赖 `module_unload` 持久化唯一一份关键数据。它与析构函数和 `defer` 一样，只保证在语言定义的正常退出与受控卸载路径上执行。

## 10. 成本模型

生命周期和事务式注册的成本发生在程序启动、动态加载、受控卸载或热更新时，不为每次普通函数调用增加注册检查。

热更新函数本身仍需要议题 16 定义的稳定入口间接层。路由查找、RPC 分派等机制本来需要的运行时分派不计作装饰器额外成本。

未使用动态加载、热更新和运行时注册的程序，可以由编译器与链接器静态生成启动和退出表，不要求通用动态模块管理器常驻。

议题 61 规定 Ink 模块以源码分发，不承诺稳定的 Ink-to-Ink 二进制模块 ABI。本议题中的模块镜像、稳定入口和版本事务是同一次兼容构建为进程内部生成的运行时协议，不能据此把私有 Ink 类、接口、异常或泛型 ABI 作为二进制库接口分发。独立二进制库必须通过 `extern "C"` 和 C ABI 安全类型建立公开边界。
