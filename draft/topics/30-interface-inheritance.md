# 议题 30：接口继承、重新抽象与接口转换

> 状态：已确认，2026-08-05 确认泛型接口复用统一泛型参数语法；2026-08-08 确认 v0 同步/异步接口覆盖结果类型必须准确一致；议题 31、35、56、60、66 与 Parser 议题 33 补充
> 确认日期：2026-08-08

## 1. 接口允许多继承

接口可以继承任意多个接口：

```ink
interface Reader {
    func read(buffer: byte[]) -> ptrsize;
}

interface Seekable {
    func seek(offset: ptrsize);
}

interface SeekableReader : Reader, Seekable {
    func position() -> ptrsize;
}
```

接口继承不受类的单一具体继承限制，因为接口没有实例字段、构造函数、析构函数或父类子对象。接口继承只组合方法契约、默认实现、元数据和接口转换关系。

接口可以声明泛型参数，并与泛型类、泛型函数复用同一套泛型参数和实例化规则，不引入接口专用泛型语法：

```ink
interface Iterable<T: type> {
    func iterator() -> Iterator::<T>;
}

interface RandomAccessRange<T: type> : Iterable::<T> {
    func at(index: ptrsize) const -> const T&;
}

class Vector<T: type> : RandomAccessRange::<T> {
    // ...
}
```

开放声明 `Iterable` 是议题 66 的 `GenericTypeDecl`，不是可直接用在继承列表中的闭合 `type`；`Iterable::<i32>`、`Iterable::<string>` 等实例分别形成不同的接口类型。泛型接口继承可以在父接口实参中引用当前接口的泛型参数，例如 `RandomAccessRange<T: type> : Iterable::<T>`。Parser 只复用统一的 `generic_parameter_clause`，并按议题 24 的 `inheritance_clause` 把每个父接口位置解析为完整 `type`；实参数量、约束、开放声明误用以及实例化后的继承关系由语义分析检查。

继承图必须是有向无环图。接口直接或间接继承自身时产生编译错误。

议题 35 的 `[exception] interface` 只能继承其他显式标记 `[exception]` 的接口。普通接口不能通过继承异常接口隐式进入可捕获类型体系。

## 2. 实现子接口同时实现全部祖先接口

类声明实现一个子接口时，必须满足该接口的完整有效方法集合，并自动建立到全部祖先接口的实现关系：

```ink
class FileReader : SeekableReader {
    override func read(buffer: byte[]) -> ptrsize {
        // ...
    }

    override func seek(offset: ptrsize) {
        // ...
    }

    override func position() -> ptrsize {
        // ...
    }
}
```

因此 `FileReader` 可以转换为 `SeekableReader&`、`Reader&` 或 `Seekable&`。它不包含任何接口父对象，也不会因为接口继承而增加对象字段或 vptr。

## 3. 有效方法集合

一个接口的有效方法集合由以下内容组成：

1. 当前接口直接声明的方法；
2. 所有直接和传递父接口继承的方法；
3. 按本议题规则合并后的必需方法和默认方法。

当前接口直接声明的兼容 `override` 优先于所有被覆盖的父接口声明。父接口在继承列表中的先后顺序不产生语义优先级，也不能用于选择默认实现。

接口继承列表的顺序可以参与目标 ABI 的确定性布局，但程序不能观察或依赖某个方法因为父接口写得更靠前而获胜。

## 4. 菱形继承按声明来源合并

同一个祖先方法经多条路径进入子接口时，只表示同一个继承方法，不构成冲突：

```ink
interface Root {
    func reset();
}

interface Left : Root {}
interface Right : Root {}

interface Diamond : Left, Right {}
```

`Diamond` 的有效方法集合中只有一个来源为 `Root.reset` 的要求。编译器可以在内部跟踪声明来源来完成合并；这种编译期来源关系不是议题 22 所禁止的公开稳定 ID，运行时动态身份仍然只使用完全限定字符串名称。

如果 `Root.reset` 具有默认实现，两条路径继承的仍是同一个默认实现，不发生默认方法冲突。

## 5. 无关接口的相同必需方法

多个无关父接口具有名称、参数、返回类型、接收者限定和调用约定都兼容的必需方法时，子接口把它们合并为一项实现要求：

```ink
interface A {
    func reset();
}

interface B {
    func reset();
}

interface C : A, B {}
```

实现 `C` 的类可以用一个兼容方法同时满足 `A.reset` 和 `B.reset`。具体类针对 `A`、`B` 和 `C` 的接口表仍是独立的；相关槽可以指向同一实现或等价 thunk。

这种合并只合并普通类型检查中的实现要求，不把 `A.reset` 和 `B.reset` 的完全限定反射描述符合并为同一个运行时身份。

## 6. 不同来源的默认方法必须显式消解

以下两种情况都形成需要子接口显式处理的冲突：

- 多个无关父接口为同一兼容签名提供不同默认实现；
- 一个无关父接口提供默认实现，另一个父接口只声明相同必需方法。

编译器不能按继承列表顺序选择默认实现。子接口必须选择以下两种处理方式之一。

### 6.1 提供新的默认实现

```ink
interface C : A, B {
    override func reset() {
        // C 为所有实现类定义统一的默认行为
    }
}
```

该声明覆盖所有签名兼容的继承候选，并成为来源为 `C.reset` 的新默认方法。

### 6.2 重新抽象为必需方法

```ink
interface C : A, B {
    override func reset();
}
```

接口中的无函数体 `override` 表示重新抽象：它显式丢弃所有匹配的继承默认实现，并把 `C.reset` 重新声明为实现类必须提供的方法。

重新抽象不是调用某个父接口默认实现，也不会隐式生成函数体。实现 `C` 的具体类必须显式覆盖 `reset`。

## 7. 接口 `override` 规则

子接口方法使用 `override` 时必须至少匹配一个继承方法，并满足普通覆盖兼容性：

- 名称和参数匹配；
- 返回类型与被覆盖根槽的逻辑结果类型准确一致；
- 接收者的可变性、错误约定和调用约定兼容；
- 不削弱契约要求。

议题 60 与 2026-08-08 的 IR/调用约定设计规定，Ink v0 的同步和异步接口方法都要求逻辑结果类型与被覆盖根槽完全一致，不允许协变结果。未来若为同步方法增加协变，必须作为独立扩展定义槽 thunk、直接调用视图和反射结果规则。

没有匹配继承方法时使用 `override` 是编译错误。存在同名但签名不同的方法时，它们仍是普通重载候选和独立接口槽；一个 `override` 只处理与自身签名兼容的候选。

接口中的 `override func f();` 专门表示重新抽象。类中的无函数体 `override` 不因此合法；具体非抽象类仍必须提供函数体。

## 8. 独立接口表

接口继承不采用 C++ 式父接口子对象，也不要求某个父接口表是子接口表的内存前缀。每个具体类—接口组合具有逻辑上独立的接口表：

```text
FileReader-as-SeekableReader table
FileReader-as-Reader table
FileReader-as-Seekable table
```

子接口表包含其有效方法集合所需的调用槽。继承方法槽按照最终合并和覆盖结果指向：

- 具体类实现 thunk；
- 子接口默认实现 thunk；
- 未被覆盖且无冲突的祖先默认实现 thunk。

不同接口表中的槽可以共享同一代码入口，但一个接口的 ABI 不通过内存前缀依赖另一个接口的槽位布局。

议题 56 的异步默认方法必须遵守这种独立布局。通过子接口表选择继承自祖先的异步默认方法时，槽适配 thunk 把接收者规范化为同一具体类对应的默认方法声明接口视图，再构造保存该视图的任务；不能把子接口表直接按祖先接口槽编号解释。

## 9. 子接口到父接口的上转型

接口引用继续使用议题 26 的两字表示：

```text
{ object, table }
```

从子接口引用上转型为父接口引用时：

- `object` 保持完整实现对象的规范地址不变；
- `table` 替换为同一具体对象类型对应的父接口表；
- 不复制对象；
- 不改变所有权或生命周期；
- 不分配内存；
- 不执行用户代码。

当具体类在编译期已知时，编译器可以直接选择父接口表。当调用者只有动态的子接口引用时，子接口表保存到各传递祖先接口表的确定性转换项：

```text
Child interface table
    methods [...]
    ancestor Reader   -> same-class-as-Reader table
    ancestor Seekable -> same-class-as-Seekable table
```

静态目标父接口决定转换项位置，因此上转型为常数时间的表读取和两个机器字的接口引用构造。无需按字符串查找，也无需遍历继承图。

父接口到子接口的下转型不是上转型的逆操作，必须使用议题 31 的 `try_cast` 进行动态类型检查。

## 10. 调用和冲突行为

通过子接口引用调用继承方法时，直接使用子接口表中的有效方法槽，不要求先构造父接口引用。

通过显式上转型后的父接口引用调用时，使用父接口自己的表和描述符。两条路径必须到达语义上相同的最终类覆盖；如果没有类覆盖，则按照本议题和议题 29 已消解的默认方法来源执行。

对于异步默认方法，“到达相同实现”还要求任务保存的声明接口视图具有相同的有效最终覆盖。具体类对应的父接口表必须反映其实现子接口后已经选定的类覆盖或子接口默认覆盖，使祖先默认函数体内部的新接口调用不会退回被覆盖的祖先实现。

继承图中尚未消解的默认方法冲突使子接口声明编译失败，而不是推迟到调用点或任意实现类。这样所有合法子接口都具有确定的有效方法集合。

## 11. 编译期与动态反射

编译期反射可以访问接口继承图的全部信息，包括：

- `direct_bases`：直接父接口；
- `ancestors`：去重后的传递祖先接口；
- `declared_functions`：当前接口直接声明的方法；
- `functions`：合并、覆盖和重新抽象后的有效方法；
- 每个有效方法的 `declaring_interface`、是否为默认方法、是否被重新抽象以及覆盖来源。

动态 `InterfaceInfo` 对 `[reflect]` 接口公开对应的反射子集。按名称查找遵循：

1. 当前接口直接声明的同名反射方法优先；
2. 否则查找父接口；
3. 同一个声明经菱形路径出现多次时只保留一次；
4. 不同来源的多个同名反射方法不能靠父接口顺序消歧。

动态描述符记录 `declaring_interface`。继承不会把 `A.reset`、`B.reset` 和 `C.reset` 变成同一个字符串身份；通过不同父接口视图查询时仍得到各自的完全限定描述符。

如果一个 `[reflect]` 子接口的有效反射视图中仍会出现不同来源的多个同名方法，编译器要求子接口显式重新声明一个同名 `[reflect] override` 来建立子接口优先的唯一描述符，否则编译错误。这保持议题 23 和 28 的“同一动态反射作用域中名称唯一”规则。

## 12. 热更新与 ABI

以下变化属于接口分派和反射 ABI 变化：

- 增加、删除或重新排序直接父接口；
- 改变继承方法的签名；
- 增加或删除重新抽象声明；
- 改变冲突消解所选择的默认实现；
- 改变有效方法槽或祖先转换项集合。

这些变化需要新的接口表和反射元数据版本，不能把旧接口引用的表直接解释为新版本；因此 Ink v0 hot reload 必须拒绝它们。新表随重新构建/重启生效，多版本表并存与对象迁移留给未来协议。

只修改已经选定的默认方法或类实现函数体而不改变签名、有效槽和转换关系时，可以按照既有稳定入口与更新事务规则替换实现，不改变对象布局。

## 13. 成本模型

接口继承不会给对象增加字段、父接口子对象或 vptr。主要静态成本是：

- 每个实际生成的具体类—接口组合对应的接口表；
- 子接口有效方法槽可能对祖先方法入口形成重复引用；
- 子接口表中到传递祖先接口表的转换项；
- 启用反射时的继承关系和方法来源元数据。

普通子接口方法调用仍通常是一次接口表槽间接调用。子接口到已知父接口的上转型是常数时间，不分配内存；转换动态子接口引用时通常增加一次转换项读取。
