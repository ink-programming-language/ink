# 议题 42：未捕获异常边界与进程级 fail-fast

> 状态：已确认，模块边界不包含用户加载或卸载钩子；议题 43、47、52、53 补充，精确运行时观测钩子 ABI 待定
> 确认日期：2026-08-02

## 1. 普通执行域采用进程级 fail-fast

未捕获 Ink 异常到达以下任一普通执行边界时，运行时必须报告可用诊断并终止整个进程：

- 程序 `main` 的运行时入口；
- 由 Ink 运行时启动的普通 OS 线程入口；
- `[nothrow]`、析构、卸载或外部 ABI 等不可抛出边界发生的运行时违约。

运行时不能在这些边界吞掉异常后恢复普通控制流，也不能默认只结束发生异常的线程而让其余线程继续运行。

## 2. 为什么不是只终止当前线程

一个线程在任意调用深度异常退出时，可能已经：

- 修改共享对象的一部分字段；
- 持有跨线程协议中的逻辑所有权；
- 完成外部事务的一部分；
- 发布了其他线程可见但尚未完成的状态；
- 中断模块、设备或服务状态转换。

RAII 可以清理已经建立的局部资源，但不能自动回滚全部共享语义和外部副作用。默认仅结束当前线程会让进程在无法证明一致的状态下继续运行，因此 Ink 选择进程级 fail-fast。

## 3. 需要线程隔离时显式捕获

程序需要把工作线程失败转换成普通状态时，必须在线程入口显式建立 catch-all：

```ink
[nothrow]
func worker_entry(state: WorkerState&) {
    try {
        run_worker(state);
    } catch as error {
        report_worker_failure(error);
        state.mark_failed();
    }
}
```

该处理器必须自己满足共享状态、同步、日志和恢复协议。异常被正常处理后，线程可以返回；这不是未捕获异常路径。

如果处理器执行 `throw;`、抛出新异常或调用会让异常逃逸的函数，线程入口仍然触发进程级 fail-fast。

## 4. 致命边界不保证继续展开或清理

一旦运行时确定异常已经到达致命执行边界，不保证为了终止进程而继续执行：

- 尚未离开的栈帧中的局部析构；
- 尚未运行的 `defer`；
- 线程局部对象析构；
- 模块全局对象析构；
- `atexit` 风格外部回调或缓冲区刷新。

实现可以在部分目标上已经完成某些展开，但程序不能依赖这种差异。致命报告之后使用立即进程终止语义，而不是正常从 `main` 返回的有序退出语义。

需要提交文件、刷新日志、关闭协议或执行业务回滚的程序必须在异常到达致命边界前显式捕获并完成这些动作。

## 5. 未捕获异常观察钩子

运行时允许安装一个进程级未捕获异常观察钩子。概念签名为：

```ink
[nothrow]
func unhandled_exception_hook(error: const core.ExceptionView&);
```

钩子可以：

- 读取异常类型和显式原因链；
- 读取 `throw_site` 和已经捕获的 traceback；
- 写入日志、崩溃报告或遥测；
- 触发调试器集成。

钩子不能修改异常、取得异常记录所有权、返回“已处理”、要求继续执行或阻止进程终止。它返回后，运行时继续默认报告和终止流程。

## 6. 钩子必须 `[nothrow]`

观察钩子是不可恢复的 `[nothrow]` 边界：

- 编译器必须拒绝能够静态证明有异常逃逸的钩子；
- 钩子内部若调用普通可能抛出函数，必须自己捕获全部异常；
- 运行时仍观察到异常越界时，不递归调用观察钩子；
- 钩子触发 trap、再次异常或其他致命错误时，运行时立即使用可用的最低限度报告终止进程。

钩子可以使用分配器和普通库，但这些操作在内存耗尽或运行时损坏场景中未必成功。高可靠崩溃日志钩子应优先使用预分配存储和 `[nothrow]` 底层输出。

## 7. 钩子生命周期与并发

钩子接收的 `ExceptionView` 及其派生视图只在本次调用期间有效，不能保存到全局、异步任务或其他线程。

未捕获异常可能由任意普通 OS 线程触发。钩子实现必须能够处理运行时并发终止竞争，不得假设只有主线程会调用它。运行时可以用一次性致命状态门选择主要报告线程，但不保证在所有目标和嵌入环境中串行化用户钩子。

钩子的安装、替换和移除必须由运行时提供线程安全操作。安装的函数入口属于具体模块版本；运行时必须使用稳定入口或固定该模块版本，直到钩子被原子替换或移除。

精确注册 API、是否允许多个观察器及其顺序留给运行时钩子 ABI；无论选择何种 API，都不能改变终止强制性。

## 8. 默认诊断顺序

概念致命流程为：

```text
detect fatal unhandled exception
    → keep ExceptionRecord and module metadata valid
    → invoke installed [nothrow] observer if available
    → emit configured built-in or fallback report
    → terminate process immediately
```

报告器至少尝试输出最外层异常的完全限定类型和 `throw_site`。议题 40、41 的原因链和 traceback 在可用时一并输出。

观察钩子或完整符号化失败不能取消终止。运行时应回退到不分配或少分配的最低限度报告；若连最低限度输出也失败，仍必须终止进程。

## 9. `main` 边界

异常离开 `main` 不等价于 `main` 返回非零值：

- 不进入正常模块卸载顺序；
- 不保证全局对象析构；
- 运行时选择目标适用的失败退出状态或致命终止机制。

需要把失败转换成稳定退出码并正常关闭模块的程序必须在 `main` 内显式捕获：

```ink
func main() -> int {
    try {
        return run_application();
    } catch as error {
        report(error);
        return 1;
    }
}
```

## 10. 普通 OS 线程边界

运行时在线程入口外围建立内部致命边界，但它不是用户可恢复的隐式 `catch`。未捕获记录仍按原类型、原因和 traceback 报告，然后启动进程终止。

异常不会被翻译成线程返回值，不会自动存入某个全局“最后线程错误”，也不会跨线程继续展开。

直接由外部库创建并回调 Ink 的线程必须通过显式 Ink ABI 适配入口进入。适配器负责建立等价边界或在返回外部 ABI 前捕获并转换异常。

## 11. 模块版本准备与回收边界

Ink 不提供用户模块加载、卸载回调，也不允许 decorator 生成这类生命周期代码。模块版本准备仍可能因全局对象初始化或运行时内部验证失败；加载器在发布边界捕获失败，将新版本视为未完成，并按议题 17、18 逆序销毁已经成功构造的全局对象、丢弃未发布注册记录。

模块准备失败的逆序清理、旧版本回收和模块全局对象析构不允许异常逃逸。编译器可见的违约必须报错；运行时仍观察到异常越过这些清理边界时进入进程级 fail-fast，不能忽略失败后继续回收其他状态。

## 12. 析构、`defer` 与 `[nothrow]`

议题 03、27 和 34 已要求析构及清理满足不抛出契约。若异常展开期间的析构、`defer` 或动态销毁入口再次抛出，运行时立即进入 fail-fast，不用第二个异常替换正在传播的异常。

普通 `[nothrow]` 函数因 ABI 破坏、外部代码错误或后端违约让异常逃逸时采用相同规则。源码调用者不能捕获一个已经越过 `[nothrow]` 边界的异常。

观察钩子可以报告运行时能够保留的主要异常和违约位置，但双异常及严重 ABI 损坏时只保证最低限度诊断。

## 13. FFI 与嵌入环境

Ink 异常不能直接展开到未知 C 或其他外部 ABI。导出包装器必须标记 `[nothrow]` 或捕获全部 Ink 异常并转换成外部错误协议。

如果异常仍然越过声明为不可抛出的 FFI 边界，运行时立即终止进程。嵌入宿主可以安装观察钩子或提供目标相关的致命报告接口，但不能通过该钩子恢复发生违约的 Ink 调用栈。

希望宿主继续运行的嵌入 API 必须在边界内部正常捕获，并把失败返回给宿主；不能把未捕获钩子当作错误返回机制。

## 14. 异步任务不是普通线程边界

异步任务边界必须捕获异常并把失败保存到任务结果，因此任务函数抛出不立即触发本议题的进程级 fail-fast。该规则属于 `Task<T>` 语义，不依赖核心语言存在某个 `Executor` 类型。

议题 43 规定任务边界把异常保存到只读、共享的 `ExceptionBox`，并将任务发布为失败终态。对失败任务执行 `await` 时，每个等待者建立独立活动展开记录，从等待点重新进入普通异常传播；同一失败任务可以重复等待。

失败任务完成本身不触发进程级 fail-fast。议题 53 规定核心 `Task<T>` 不记录失败是否曾被观察；发布或析构 `failed` 任务都不打印、不抛出，也不进入 fail-fast。

议题 47 的 `all` 和 `all_cancel_on_error` 会检查全部输入的最终状态。多个输入失败时，未被选中传播的失败按普通所有权规则清理；核心语言没有 observation bit 或未观察失败诊断需要更新。库级后台设施仍可按议题 52 在自己的对象中实现日志或 fail-fast 策略。

普通 OS 线程没有这种隐式任务结果协议，除非程序显式使用提供等价结果对象的线程库包装。

## 15. 成本与 LLVM 实现

普通函数调用不检查是否存在未捕获异常。运行时只在 `main`、线程入口、模块清理、FFI 和其他明确边界设置包装或验证逻辑。

安装观察钩子的成本只发生在致命路径。没有未捕获异常时，不调用钩子、不格式化报告，也不遍历原因链或 traceback。

LLVM 已有 personality、landing pad、funclet、`nounwind` 和进程终止调用足以实现这些边界。Ink 前端和运行时生成入口包装、保存 `ExceptionView` 并调用钩子；无需修改 LLVM 源码。

## 16. 后续问题

以下内容仍留给后续议题或运行时 ABI：

- 未捕获观察钩子的精确安装、替换和多观察器 API；
- 目标平台退出状态、立即终止原语和崩溃转储集成；
- 并发线程同时失败时的主报告线程选择；
- freestanding、内核和无进程环境中的致命执行域；
- trap、硬件故障和操作系统信号的独立报告机制。

核心失败任务的观察状态与析构报告策略已经由议题 53 确定，不再是待定项。
