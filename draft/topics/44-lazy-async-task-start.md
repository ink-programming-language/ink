# 议题 44：惰性异步任务与 `await` 驱动执行

> 状态：已确认，议题 45、48—52、54—59、65 修订；高层调度属于库，底层任务驱动 ABI 待定
> 确认日期：2026-08-02

## 1. 调用异步函数只创建任务

调用 Ink 异步函数时，默认只创建一个尚未执行的惰性 `Task::<T>`：

```ink
async func load() -> int {
    print("start");
    return read_value();
}

var task = load();
// 此处尚未打印 start
```

异步函数声明省略 `-> type` 时逻辑结果固定为 `void`，调用产生 `Task::<void>`，同样不根据函数体推导结果：

```ink
async func notify() {
    return;
}

var task: Task::<void> = notify();
```

异步函数体不会仅因为调用表达式完成而执行，也不会自动提交给线程池、事件循环或其他调度设施。

议题 58 的普通异步装饰器属于该函数体。构造装饰后任务不会立即运行装饰器前置或后置代码；它们与原始函数体一起等到任务第一次被驱动。

议题 59 确认 v0 不开放围绕本节同步创建阶段的任务构造装饰器。需要创建期用户逻辑时使用显式同步任务工厂返回 `Task::<T>`；该工厂的同步副作用在调用时运行，返回任务的异步函数体仍保持惰性。

议题 65 的省略默认实参也在调用点同步求值，并在进入任务构造入口前补全。默认表达式的副作用不属于惰性异步函数体；需要报告可恢复问题的默认表达式必须通过普通值表达状态。

因此创建后从未等待、从未交给组合等待，也未被库通过底层任务驱动接口接管的任务不会执行函数体及其副作用。

## 2. 任务区分未执行与执行中状态

议题 43 的任务状态补充为：

```text
TaskState::<T> =
    created
    pending
    succeeded(ResultStorage::<T>)
```

状态转换至少满足：

```text
created
    → pending
        → succeeded
```

`created` 表示协程帧、实参和固定模块入口已经准备完成，但函数体尚未运行。`pending` 表示任务已经被等待操作或调度库驱动，可能正在运行，也可能暂时挂起或等待调度。

任务一旦离开 `created` 就不能重新初始化或再次执行函数体。最终状态仍遵守议题 43 的不可变和可重复观察规则。

## 3. 第一次直接 `await` 驱动任务

对 `created` 状态的任务执行 `await` 时，等待操作先驱动任务进入 `pending`，然后等待其最终状态：

```ink
var task = load();

const value = await task; // 第一次 await 开始执行 load
```

概念行为为：

```text
await task
    → if state == created: enter pending exactly once
    → if state == pending: suspend or register continuation
    → if state == succeeded: copy result
```

如果任务在本次等待过程中不发生真正挂起，实现可以直接继续运行并返回结果；语言不要求为了形式上的异步而强制切换线程或执行一次无意义调度。

## 4. 不提供公开的 `Task.start()`

`Task::<T>` 不提供只启动而不等待的公开 `start()` 操作：

```ink
var task = load();
task.start(); // 编译错误：Task 没有公开 start 操作
```

这避免局部任务已经开始运行、控制流却绕过后续 `await`，从而留下仍在运行且生命周期无人负责的任务。

需要让多个惰性任务并发前进时，使用议题 45 的组合等待：

```ink
const (first, second) = await all(load_a(), load_b());
```

需要让工作脱离当前等待表达式长期运行时，必须通过显式库 API 把工作交给能够维持其存储和生命周期的调度设施；核心语言不提供统一 `spawn`，具体规则由所选库定义。

运行时内部仍然存在把 `created` 原子转换为 `pending` 的协议。它是 `await`、`all` 和议题 52 的调度库底层接口使用的受约束能力，不是局部代码可以调用后忘记收尾的通用 `Task.start()`。

## 5. 并发首次等待只驱动一次

多个等待者可能通过 `Task::<T>*` 同时对一个 `created` 任务执行第一次 `await`：

```text
waiter A ─┐
          ├── atomic drive gate ── one task execution
waiter B ─┘
```

运行时必须保证：

- 只有一个等待者成功使任务进入 `pending`；
- 其他等待者登记为普通 continuation；
- 函数体永远只执行一次；
- 完成发布与 continuation 登记之间不存在丢失唤醒；
- 所有等待者最终观察议题 43 的同一只读完成终态。

这通常需要一次原子状态转换或由单线程运行时调度器提供等价串行化。

## 6. 实参在调用点求值

惰性只适用于异步函数体，不推迟调用表达式本身的实参求值：

```ink
var task = load(make_path());
```

`make_path()` 按普通调用的求值规则立即执行。其结果、函数参数和异步函数以后运行所需的捕获状态在 `task` 创建完成前存入任务帧。

因此：

- 实参表达式的副作用发生在创建任务时；
- 需要表达可恢复问题的实参计算使用普通返回值或状态；
- 异步函数体内的副作用推迟到任务被驱动后；
- 调用点完成后，异步函数体不能再借用已经结束的普通参数临时量。

这使惰性任务的参数快照在创建时确定，而不是等到未来执行时重新求值表达式。

## 7. 参数捕获遵守复制和地址规则

任务帧属于长期存储，异步参数在任务创建时按以下规则保存：

- 可复制的按值参数按议题 02 复制到任务帧；
- 没有独立源对象的构造表达式可以直接构造在任务帧中；
- 命名的 `[noncopyable]` 对象不能通过按值异步调用隐式移动进任务；
- `T&`、`const T&` 可以作为非拥有地址别名保存，程序员负责保证目标生命周期；
- 原始指针和原始切片同样按值保存并由程序员保证生命周期；
- 安全切片仍不能被任务帧长期保存。

```ink
async func inspect_later(file: File*) {
    file->inspect();
}

var task = inspect_later(&file);
await task;
```

这里 `File*` 在任务创建时复制进帧。程序必须保证 `file` 一直存活到任务不再访问它；惰性执行不会延长目标对象生命周期。

议题 54 规定异步成员函数不需要额外写出指针接收者参数。普通 `object.method_async()` 调用在创建任务时隐式取得对象地址，并把它作为非拥有原始 `this` 指针保存进帧；不复制对象。该接收对象必须保持在原地址并存活到任务最终结束，后续访问遵守普通 `File*` 的地址和并发前置条件。普通引用参数具有相同的非拥有生命周期风险。

## 8. 任务构造必须完整成功

调用表达式先求值全部实参，再初始化参数、捕获状态、任务帧和稳定模块入口。只有这些步骤完整结束后，调用者才取得 `Task::<T>`；语言不会暴露部分构造的任务。

能够恢复的参数检查和资源状态必须在普通返回类型中表达。需要同步准备资源的 API 可以提供显式工厂，先返回项目定义的状态，再由调用者决定是否创建异步任务。宿主内存耗尽或运行时状态损坏属于无法可靠恢复的进程级故障。

任务成功创建后，异步函数体只通过普通 `return` 发布 `T`。需要区分业务结果时，`T` 自身应是状态枚举、带标签联合、可空指针或项目定义的其他普通结果类型。

调度库接受工作时的资源耗尽、队列关闭等情况由该库的显式 API 契约处理，不属于异步调用表达式的核心语言语义。

## 9. 未执行任务不产生函数体行为

从未被驱动的任务没有执行过异步函数体，因此：

- 不产生函数体副作用；
- 不建立函数体局部对象；
- 销毁时只需要清理已经建立的帧、实参和运行时状态。

编译器应对明显创建后立即丢弃、从未 `await`、传给组合等待、传给能够接管任务的库接口、返回或保存的任务给出 warning。该 warning 用于发现漏写等待，不把惰性任务改成隐式执行。对任意普通库调用能否证明“接管”属于静态分析能力，不要求编译器按函数名称猜测。

该 warning 只表示任务函数体不会执行，不代表任务已经运行或产生了某种业务结果。

## 10. 热更新绑定发生在任务创建时

惰性任务在创建时固定异步函数的具体模块版本和稳定入口，而不是等到第一次被驱动时重新按名称查找最新实现：

```text
create task under module version V1
    → hot update installs V2
    → await old task
    → task still executes V1 body and V1 frame ABI
```

这样可以保证：

- 创建时建立的帧布局与执行代码匹配；
- 参数和局部状态不会被新版本按不同布局解释；
- 同一个任务不会因为开始执行的时间不同改变行为；
- 销毁入口、类型元数据和调试信息来自兼容版本。

代价是一个长期未执行的惰性任务也可能固定旧模块版本。只有任务对象及其帧完全释放后，运行时才能解除该固定关系。

议题 55 将同一原则用于类异步虚函数：方法调用时先从 vtable 选择最终覆盖，再构造并固定该覆盖的任务；第一次 `await` 不能重新虚派发到更新后的实现。

议题 56 对异步接口调用采用相同原则。议题 57 的 `FunctionInfo.call_async::<R>` 只增加创建期反射检查，并进入普通静态、虚或接口任务构造路径；它不驱动任务，也不把反射名称查找推迟到第一次 `await`。

议题 58 进一步规定被选实现的完整异步装饰器链和原始函数体固定为同一个任务版本。热更新不会让旧任务在开始执行时改用新装饰器展开；普通异步装饰器也不能观察调用表达式中的同步任务构造阶段。

## 11. 连续直接 `await` 表达顺序执行

连续直接等待两个新任务时，第一项完成后才会创建并驱动第二项：

```ink
const first = await load_a();
const second = await load_b();
```

即使先创建两个任务，直接等待仍然按照控制流顺序驱动：

```ink
var first_task = load_a();
var second_task = load_b();

const first = await first_task;
const second = await second_task;
```

第二个任务在执行到第二个 `await` 前仍处于 `created`。编译器不得根据未来的等待、最后一次使用、优化级别或目标平台擅自提前驱动它。

需要并发时必须明确写出议题 45 的 `await all(...)`，使并发关系成为源码语义。

## 12. 调度与后台执行属于库

议题 52 规定核心语言不提供内建 `Executor`、`spawn`、`spawn_detached`、任务组或控制句柄。标准库和第三方库可以使用普通类型与函数提供这些功能，并自行定义调度、所有权、失败、回收和关闭策略。

库不能因此隐式移动已经存在的命名 `Task::<T>`。它必须使用 `Task::<T>*` 并要求有效生命周期，或者通过底层任务驱动 ABI 在库拥有的稳定存储中直接构造任务。局部 `Task::<T>` 仍然没有公开 `start()`。

## 13. 与任务销毁和取消的关系

普通局部任务如果从未被等待，可以作为 `created` 任务直接清理，而不会执行函数体：

```ink
func example() {
    var task = work_async();
} // 只清理 created 任务；编译器可以 warning
```

议题 45 的 `all` 必须负责其驱动的全部任务直到它们结束。任何允许后台执行的库 API 也必须先取得足够长的存储和明确的生命周期责任；核心语言不允许局部代码把任务启动后立即遗忘。

议题 48 确定取消请求不产生特殊任务终态。议题 49 确定普通任务通过线程安全的 `Task.request_cancel()` 接收请求；调度库如果提供额外控制句柄，其取消和销毁策略属于库契约，但不能破坏底层 `Task::<T>` 的语言级状态规则。

议题 51 规定局部 `Task::<T>` 只有在 `created` 或 `succeeded` 状态下才能正常析构；析构 `pending` 任务立即触发致命 trap。请求取消不能代替等待任务结束。

## 14. 成本模型

创建惰性任务可能需要：

- 构造任务对象和状态机帧；
- 保存实参、捕获状态和模块版本入口；
- 取得必要存储；
- 初始化一次性驱动门。

它不执行异步函数体，不登记 I/O，也不提交调度队列。

第一次直接 `await`、议题 45 的组合等待或调度库通过底层接口接管任务时，承担一次状态转换和必要调度。后续重复 `await` 不再次执行函数体，只使用议题 43 的完成状态协议。

编译器可以消除能够证明不需要的中间任务对象、帧分配或调度，但不得提前执行用户可观察的异步函数体，也不得把源码中的顺序等待自动改成并发执行。

## 15. LLVM 与运行时实现

该设计不需要修改 LLVM 源码。前端可以通过 LLVM coroutine intrinsics 或自行生成的状态机实现：

```text
async call:
    evaluate arguments
    construct coroutine frame in suspended initial state
    record stable entry and module version
    return Task::<T>

first direct await / all / library task driver:
    atomic created → pending
    resume directly or submit coroutine handle to a library scheduler

later await:
    register continuation or observe immutable final state
```

LLVM 的 coroutine `initial_suspend` 能表达初始暂停，普通原子操作能实现一次性驱动门。任务状态和模块固定由 Ink 运行时管理，具体调度策略由库管理；LLVM 不需要理解惰性执行或库调度的语言语义。

## 16. 后续问题

以下内容留给后续议题：

- 底层任务驱动接口及稳定存储中的原地构造 ABI；
- 帧内联、分配器、任务池和精确 ABI；
- 编译器未使用任务 warning 的抑制方式。

`spawn`、join、detach、任务组、执行器选择、调度提交失败和执行器关闭均已由议题 52 划归库设计，不再作为核心语言待定项。
