# 议题 52：任务调度与后台执行属于库

> 状态：已确认，议题 53 补充库级失败观察策略  
> 确认日期：2026-08-02

## 1. 核心语言不提供 `spawn`

Ink 核心语言不定义下列高层调度设施：

- 内建 `Executor` 类型；
- `spawn` 或 `spawn_detached` 关键字；
- `TaskHandle::<T>`、`JoinHandle::<T>` 等内建控制句柄；
- 内建任务组、线程池或全局事件循环；
- 统一的 detach、join、调度优先级和执行器关闭策略。

`Executor`、`spawn`、`spawn_detached`、`TaskHandle` 等名称不保留。标准库或第三方库可以把它们作为普通标识符使用，但这些 API 不获得编译器特殊语义。

## 2. 核心异步语义保持最小

核心语言只确定此前已经确认的语义：

- 调用 `async func` 创建惰性 `Task::<T>`；
- 普通 `Task::<T>` 没有公开 `start()`；
- 在普通源码中，第一次直接 `await` 或议题 45 的组合等待驱动任务；调度库只能通过本议题规定的底层任务驱动接口显式接管；
- `Task::<T>` 的完成、异常、取消请求和析构遵守议题 43—51；
- 编译器不会把普通异步调用自动提交到隐藏的全局线程池或事件循环。

因此最普通的异步代码不承担后台调度所需的队列、长期所有权、线程同步或独立控制句柄成本。

## 3. 高层调度策略由库定义

库可以按自己的用途提供：

- 单线程事件循环；
- 工作窃取线程池；
- 固定线程或线程亲和调度器；
- GUI、游戏循环、实时系统或嵌入式调度器；
- 后台任务、任务组、动态任务集合和最大并发数；
- join、detach、优先级、截止时间和关闭策略；
- 调度失败、未查询或未处理失败以及日志报告策略。

例如某个库可以自行定义：

```ink
var scheduler = library.ThreadPool(worker_count);
var job = scheduler.submit(work_factory);
```

另一个库可以采用完全不同的名称、句柄类型和生命周期协议。上例只说明普通库 API，不是 Ink 标准语法，也不指定标准库必须提供这些名称。

## 4. 机制与策略分离

“交给库”不表示库只能猜测编译器生成的协程布局。Ink 编译器和任务运行时必须提供可文档化的底层任务驱动接口，使调度库能够：

- 在调用方提供的稳定存储中直接构造任务；
- 原子地使 `created` 任务进入 `pending`，并保证只驱动一次；
- 恢复任务状态机；
- 登记、解除和唤醒 continuation；
- 观察不可变的最终状态；
- 发布议题 49 的取消请求；
- 按议题 51 的状态规则销毁任务。

这些能力属于编译器、核心运行时和库之间的底层 ABI，不引入 `spawn` 语言关键字，也不规定线程池、队列和后台任务策略。精确函数名、可见性和 ABI 留给任务运行时实现议题。

核心实现可以把低层入口放在受约束的 `core` 模块中。第三方调度库可以在满足前置条件的情况下使用文档化入口，不要求修改编译器来增加新的调度策略。

## 5. 库不能通过调度隐式移动任务

议题 02 的复制规则继续适用。命名的 `[noncopyable] Task::<T>` 不能因为传给某个调度库就被隐式移动：

```ink
func submit_by_value(task: Task::<int>) {
    // 普通按值参数
}

var task: Task::<int> = operation();
submit_by_value(task); // 编译错误：不能按值复制或移动 Task
```

调度库可以选择以下显式方式：

- 接收 `Task::<T>*`，并要求调用方保证任务及其引用对象的生命周期；
- 接收一个可保存的工厂或调用描述，在库拥有的稳定存储中直接构造任务；
- 定义自己的拥有型指针、控制块或句柄类型，并公开其成本和所有权规则。

库若使用引用计数、动态分配、队列复制或原子同步，这些都是所选库 API 的显式成本，不会反向成为所有 Ink `Task::<T>` 的默认成本。

## 6. 库仍受核心任务规则约束

调度设施属于库，不代表它可以绕过语言级任务状态：

- 同一个 `Task::<T>` 的函数体仍只能执行一次；
- 结果和 `ExceptionBox` 发布后仍不可变；
- 对任务的取消仍只是协作式请求；
- 不能释放仍为 `pending` 的任务帧；
- 通过原始指针访问时仍由程序保证目标生命周期与并发同步；
- 任务创建时固定的模块版本不能被调度库替换。

库定义的 detach 或后台执行 API 必须自己取得并维持足够长的存储生命周期。局部 `Task::<T>` 的析构函数不会替库执行隐式所有权转移。

## 7. 失败与关闭策略不是语言统一行为

不同调度库可以明确选择：

- 提交失败时同步抛出异常或返回库自定义结果；
- 后台任务失败时 fail-fast、记录日志、调用处理器或保存供以后查询；
- 关闭时等待任务、先请求取消再等待、拒绝关闭或采用其他显式协议；
- 已完成任务由句柄释放、由调度器批量回收或由用户显式回收。

这些选择必须由库 API 和文档说明。无论选择哪种策略，普通异常都不能越过议题 42 的 OS 线程致命边界，任务存储也不能在仍被执行时释放。

议题 53 规定核心 `Task::<T>` 没有 observation bit，析构 `failed` 任务也不会触发报告钩子。需要识别“后台任务失败但无人查询”的库必须在自己的 job、future 或控制块中显式记账，不能依赖核心任务替它完成。

## 8. 动态任务集合也属于库

议题 45 的 `all(a, b, c)` 处理源码中固定数量的组合等待。循环中不断产生的同质任务集合、任务组和并发度限制不增加新的核心语言构造，由库使用本议题的任务驱动接口实现。

核心语言不提供内建 `TaskGroup`，也不要求所有调度库采用结构化并发、非结构化并发或某一种固定任务树模型。

## 9. LLVM 实现

该决定不需要修改 LLVM 源码。Ink 前端可以使用 LLVM coroutine intrinsics 或自有状态机生成任务帧，并把恢复函数指针、状态和 continuation 操作通过普通运行时 ABI 暴露给库。

库实现的调度器只需要使用普通函数调用、原子操作、锁、线程和操作系统 I/O API。LLVM 无须认识 `Executor`、`spawn`、任务组或调度策略。

## 10. 后续问题

仍需单独确定：

- 底层任务驱动接口的精确类型、函数名和可见性；
- 稳定存储中的原地任务构造 API；
- coroutine handle、continuation 和唤醒器 ABI；
- freestanding 目标可以提供的最小任务运行时；
- 标准库是否附带某种可选调度库。

这些是运行时 ABI 或库设计问题，不重新引入核心语言级 `spawn`。
