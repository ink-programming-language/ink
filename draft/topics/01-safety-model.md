# 议题 01：运行时检查、底层契约与未定义行为

> 状态：已确认，后经议题 04、32、51、54 与 Parser 议题 25 修订
> 确认日期：2026-08-01

## 1. 不提供 `unsafe` 关键字

Ink 不提供以下语法或类型效果：

- `unsafe` 关键字；
- `unsafe { ... }` 作用域；
- `unsafe func` 函数修饰符；
- safe/unsafe 函数类型之分。

Ink 是允许程序员直接管理地址和生命周期的系统编程语言。原始指针解引用、指针成员访问、指针索引、FFI 和设备访问不要求额外语法标记。

```ink
func checksum(data: const byte*, length: ptrsize) -> u32 {
    var result: u32 = 0;

    for (const index in 0 .. length) {
        result += data[index];
    }

    return result;
}
```

调用方负责满足指针和底层 API 的前置条件。违反这些条件属于程序代码错误。

## 2. 高层操作仍然具有定义明确的检查

取消 `unsafe` 关键字不表示取消语言检查。能够由高层类型可靠检测的错误必须产生规范定义的结果：

- 数组和安全切片越界产生 trap；
- 对 `none` 执行要求值存在的操作产生 trap；
- 无效枚举判别值通过受检查转换时产生失败或 trap；枚举有效表示和默认布局由议题 32 规定；
- 析构仍为 `pending` 的 `Task<T>` 产生致命 trap；任务状态足以执行该检查，规则由议题 51 规定；
- 可以恢复的资源错误通过错误处理机制返回。

这些行为不能在优化构建中被静默删除，也不能因为对应操作在 C 或 C++ 中属于 UB 而失去语义。

整数除法和移位的边界输入由议题 09 规定为 PDB，不属于本节所列的高层强制检查。

```ink
func read(items: const int[], index: ptrsize) -> int {
    return items[index]; // 越界必定 trap
}
```

## 3. 原始内存操作的前置条件

通过原始指针读取或写入 `T` 时，程序必须保证：

- 指针在完整访问期间指向可访问存储；
- 指针满足 `T` 的对齐要求，或者使用明确的非对齐访问 API；
- 读取的存储已经初始化为有效的 `T` 表示；
- 访问范围没有越过实际可访问存储；
- 对象尚未结束生命周期或被释放；
- 访问满足并发内存模型和设备内存规则。

违反上述条件可能产生 UB。持有、复制、比较或保存空悬指针本身不访问内存，因此合法；通过空悬指针访问内存才违反前置条件。

Ink 的 UB 只来自规范明确列出的底层前置条件，不能直接继承 C/C++ 的全部 UB。编译器只能利用 Ink 规范明确授予的假设进行优化。

## 4. 底层 API 的契约

要求调用方维护地址、长度、别名、线程或生命周期关系的函数必须在文档和规范中明确列出前置条件，但函数类型本身不携带 `unsafe` 效果。

```ink
func submit(file: File*) {
    task_queue.store(file);
}
```

如果后台任务会解引用该指针，调用方必须保证 `File` 对象存活到任务不再使用它为止。语言不通过借用检查器或生命周期参数证明这一关系。

议题 54 对异步成员函数采用一个更易检查的保守契约：普通成员调用把接收对象地址作为原始 `this` 指针保存进惰性任务，接收对象必须保持在原地址并存活到该任务到达最终状态。编译器能静态证明违约时给出 warning，但不增加运行时存活检查；真正通过失效地址访问仍属于普通原始指针 UB。

标准库应当在适合的场景提供带边界和状态检查的高层 API，但不会禁止程序直接选择原始指针接口。

## 5. trap 与 UB 的边界

Ink 使用以下原则区分 trap 与 UB：

- 高层类型携带了足以检查的信息时，违约产生 trap 或普通错误；
- 原始操作缺少可靠检查所需的边界、生命周期或对象身份信息时，违约可以是 UB；
- 实现可以在调试、sanitizer 或强化构建中检测更多底层错误并产生 trap；
- 是否启用附加检测不能改变正确程序的语义。

因此安全切片越界必须 trap，而只有一个裸地址的原始指针越界访问可以产生 UB。
