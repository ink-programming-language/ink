# 议题 36：异常记录、对象存储与释放

> 状态：已确认，议题 37、38、40—43 补充，精确运行时 ABI 待定  
> 确认日期：2026-08-02

## 1. 运行时拥有异常记录

每个正在传播或处理的异常由 Ink 运行时拥有一个逻辑 `ExceptionRecord`。异常对象作为记录的载荷存在，而不是借用抛出点的局部变量：

```text
ExceptionRecord {
    unwind_header
    descriptor
    payload_size
    payload_alignment
    destroy_entry
    cause_record
    throw_site
    traceback_storage
    payload
}
```

这些字段规定语义职责，不固定所有目标上的逐字节布局：

- `unwind_header` 与目标平台的展开器交互；
- `descriptor` 指向议题 35 的最小异常描述符；
- `payload_size` 和 `payload_alignment` 描述最派生异常对象的存储要求；
- `destroy_entry` 销毁最派生异常对象并执行完整析构链；
- `cause_record` 按议题 40 可选地拥有直接原因记录，没有原因时为空；
- `throw_site` 按议题 41 指向编译器生成的静态抛出位置描述；
- `traceback_storage` 可选地引用实际抛出时捕获的原始栈帧地址；
- `payload` 是异常对象的最终存储。

分配来源、模块固定令牌和运行时内部状态可以放在记录的目标专用扩展、头部或旁表中，不是用户可观察的对象字段。

## 2. 直接构造到最终载荷

直接抛出一个没有独立源对象的构造表达式时，编译器先向运行时取得足够大小和对齐的异常记录，再把对象直接构造到 `payload`：

```ink
throw FileNotFound { path };
```

概念顺序为：

```text
acquire exception record
    → construct FileNotFound directly in payload
    → activate unwind
```

这里没有独立临时对象，也没有隐式移动。不可复制异常类可以使用这种形式抛出。

只有能够保证直接初始化最终异常载荷的构造表达式才能通过这条规则抛出不可复制类型；实现不得在不能原地构造时退化为隐藏移动。

## 3. 从命名变量抛出表示复制

从已经存在的命名变量抛出属于议题 02 的按值使用：

```ink
var error = ParseError { position: 12 };
throw error;
```

编译器把 `error` 复制到新异常记录的 `payload`，源变量仍然有效。该写法只有在异常类可复制时合法；对 `[noncopyable]` 异常类产生编译错误。

Ink 不把 `throw error` 解释为消费、移动或“最后一次使用时自动转移”。需要抛出不可复制异常时，应直接构造新的异常对象：

```ink
throw NoncopyableFailure { resource_id };
```

异常接口引用只是借用视图，不能作为新异常对象直接抛出。

## 4. 捕获只借用载荷

匹配处理器后，`catch Type as name` 按议题 35 建立对记录载荷的只读普通引用：

```text
concrete catch  → const ConcreteError&
interface catch → { payload address, exception-interface table }
```

捕获本身不复制、不移动也不重新分配异常对象。绑定名称只在处理器规定的词法作用域内可见；复制出的普通引用可以进入长期对象、全局、闭包或异步任务，但不延长记录载荷生命周期。记录失效后继续访问该引用属于 UB。

议题 38 进一步规定所有捕获绑定和活动异常载荷在语言层面永久只读，不存在把当前记录重新绑定为可变引用的处理器语法。

## 5. 重新抛出复用同一记录

从处理器重新抛出当前异常时，运行时继续使用同一个 `ExceptionRecord`：

- 不重新分配记录；
- 不复制或移动载荷；
- 保留原始动态异常类、描述符和接口集合；
- 继续从外层处理区域搜索处理器。

议题 37 选择 `throw;` 作为重新抛出语法。它只在当前处理器中合法，并遵守上述记录复用语义。

## 6. 销毁对象与释放记录分离

异常最终被处理且不再重新抛出时，运行时按以下顺序结束其生命周期：

```text
destroy_entry(payload)
    → release ExceptionRecord storage
```

`destroy_entry` 根据记录创建时固定的最派生异常类执行完整析构链。对象销毁完成后，运行时才按照记录的实际分配来源释放存储。

记录具有 `cause_record` 时，运行时先保持原因记录有效，销毁并释放当前记录，再按相同规则释放原因链。实现可以迭代处理长链，不要求使用宿主调用栈递归销毁。

两个步骤必须分离：销毁入口不能猜测记录来自线程本地区域、对象池、普通分配器还是紧急记录，也不能自行调用一个固定的全局 `free`。

析构函数继续遵守议题 03 和议题 34 的 `[nothrow]` 要求。异常展开或处理期间的清理再次抛出、或者销毁入口破坏其契约时，程序立即终止，不能用第二次展开覆盖正在销毁的记录。

## 7. 同一线程可以同时存在多个活动记录

运行时不能假设每个线程最多只有一个异常记录。外层异常仍处于处理器中时，处理器可以调用会抛出另一个异常的代码；新的异常记录与旧记录具有独立生命周期。

线程本地优化区或对象池必须支持这种嵌套情况，或者在容量不足时回退到普通异常分配器。实现不能仅用一个会被后续抛出覆盖的固定线程本地槽。

## 8. 分配模型与分配失败

Ink 不保证抛出异常是零分配操作。运行时可以按照目标和构建配置选择：

- 线程本地小对象区域；
- 异常记录对象池；
- 普通运行时分配器；
- 容量不足后的分配器回退路径。

具体阈值、池大小和分配器接口属于目标运行时 ABI，不是源码可依赖的跨平台常量。

取得异常记录的底层操作本身不能通过再次抛出普通异常来报告失败，否则会造成递归异常分配。运行时应保留至少一条紧急记录路径；如果所需载荷的大小或对齐仍无法由紧急路径承载，或者紧急资源也已不可用，程序立即终止。

紧急记录只保证异常系统能够进入定义明确的失败路径，不保证任意大小异常对象都能在内存耗尽后继续传播。

## 9. 正常路径成本

没有真正抛出异常时，函数正常执行路径不会：

- 访问异常对象池或线程本地异常区域；
- 分配 `ExceptionRecord`；
- 构造异常对象；
- 为潜在异常对象增加引用计数。

正常路径仍承担议题 34 已确认的展开表、清理边和代码尺寸成本。真正抛出时才承担记录取得、载荷构造、处理器搜索、栈展开、清理与最终销毁成本。

## 10. 模块版本与热更新

活动异常记录必须固定创建它的模块布局版本，以及处理该记录所需的：

- 最小异常描述符；
- 异常类父链数据；
- 异常接口表和 thunk；
- `destroy_entry` 及其调用的析构代码。

因此旧模块版本停止接收新调用后，仍可能因为活动异常记录而不能卸载。只有相关记录全部处理、销毁并释放后，运行时才能解除这些固定关系。

热更新不能把旧记录的载荷按同名新类型重新解释，也不能将其销毁入口替换成只理解新布局的实现。

## 11. 线程、异步与长期保存

普通 `ExceptionRecord` 属于当前同步展开和处理过程，不能直接跨线程传播，也不能由 `catch` 引用延长生命周期。普通引用本身可以跨线程传递，但若记录已经销毁，访问它就是悬空引用 UB；即使记录仍然存在，并发访问也必须满足内存模型。

议题 42 的致命未捕获路径只保证记录在观察钩子和最低限度报告期间保持有效。进程随后立即终止，不保证调用 `destroy_entry`、释放记录或解除模块固定；操作系统进程回收取代正常语言级清理。

议题 43 定义任务边界使用运行时拥有型 `ExceptionBox` 保存异常。任务边界可以把当前活动记录及其原因链重新归属到不可变 box；如果活动记录已经来自另一个失败任务，则直接保留原 box。普通同步 `catch` 不能把 `ExceptionView` 或捕获引用提升为 box，因此同步异常记录不会因为普通捕获而隐式变成共享引用计数对象。

每次对失败任务执行 `await` 都建立独立的活动展开记录；该记录内部持有共享 box，捕获结束后释放持有。异常载荷本身不复制、不移动，并一直固定原模块版本，直到失败任务状态和全部活动展开记录都释放它。

## 12. LLVM 实现

该设计不需要修改 LLVM 源码。Ink 前端和运行时负责异常记录、描述符、载荷构造和释放；LLVM 只负责生成目标支持的异常控制流与展开信息。

在采用 Itanium 风格异常 ABI 的目标上，Ink 可以把目标要求的展开头与 Ink 私有记录和载荷放在同一分配块中，通过 personality function 从展开头恢复逻辑 `ExceptionRecord`。

在 Windows 目标上，LLVM 的 SEH/funclet 降低可以让平台异常状态引用或恢复同一个逻辑记录；物理布局无须与 Itanium 目标相同。

前端可使用 LLVM 已有的 `invoke`、landing pad、personality、cleanup pad 和 funclet 等 IR/API 生成这些路径，不需要让 LLVM 理解 Ink 异常载荷的语言语义。
