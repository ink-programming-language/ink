# 议题 27：自动动态销毁与存储释放分离

> 状态：已确认，2026-08-04 同步采用 `func ~ClassName()`；2026-08-08 确认 v0 普通布局兼容对象经 stable destroy slot 使用当前实现；议题 34、36、43 补充，拥有型多态容器 API 待定
> 确认日期：2026-08-08

## 1. 不提供 `virtual` 析构函数负担

Ink 不要求用户为了通过基类销毁派生对象而给析构函数添加 `virtual`。

每个议题 26 定义的虚类 vtable 都由编译器自动生成一个动态销毁入口。该入口知道对象的最派生完整类型，并执行完整析构链。

```ink
[noncopyable]
class Entity {
    virtual func update() {
        // ...
    }

    func ~Entity() {
        // 普通析构函数，不写 virtual
    }
}

[noncopyable]
class Player : Entity {
    func ~Player() {
        // ...
    }
}
```

用户源码使用 `func ~ClassName()` 声明析构函数。动态销毁入口是编译器生命周期 ABI，不是可以直接调用或反射查找的普通函数。

函数级 `final` 不用于析构函数：用户析构函数不是源码可覆盖的虚函数槽。`final class` 仍可拥有主 vptr 和自动动态销毁入口；禁止继续派生不会改变该类自身及其既有父类析构链。

## 2. 虚类始终具有动态销毁入口

一个类只要具有主 vptr，其 vtable 就具有动态销毁入口，即使该类没有用户定义析构函数。

没有用户析构函数时，编译器生成的入口仍负责：

- 销毁最派生类字段；
- 按继承链销毁父类子对象；
- 调用字段和父类需要的析构函数；
- 维护对象生命周期结束状态。

自动存在的销毁入口不等于用户声明了析构函数，不会单独触发议题 02 的 `[noncopyable]` 要求。一个没有显式析构、且父类和字段都可复制的虚类仍可复制。

## 3. 析构顺序

动态销毁必须与静态已知完整类型的正常 RAII 销毁具有相同可观察顺序：

```text
最派生类用户析构函数
    → 最派生类字段逆序析构
    → 直接父类用户析构函数
    → 直接父类字段逆序析构
    → 继续沿具体父类链
```

如果某一层没有用户析构函数，跳过该函数但仍清理其字段和父类子对象。

用户析构函数依然不能直接调用，也不能手动调用父类析构函数。编译器负责确保每一层恰好清理一次。

## 4. 静态销毁与动态销毁

编译器知道对象完整静态类型时，可以直接生成该类型的析构链，不要求通过 vtable：

```ink
{
    const player = Player();
} // 静态销毁完整 Player
```

只有通过类型擦除的拥有关系或基类拥有关系结束对象生命周期时，才需要 vtable 动态销毁入口。

非拥有的基类引用和指针不能销毁对象：

```ink
const entity_ref: Entity& = player;
const entity_ptr: Entity* = &player;

// 二者都只是借用/原始地址，不获得销毁权限
```

这与议题 04 中“引用和原始指针不拥有目标对象”的规则一致。

## 5. 非虚基类不能动态销毁派生对象

如果基类没有主 vptr，它就没有动态销毁入口。派生到该基类的普通指针或引用上转型仍然合法，但不能据此建立一个只知道该基类、却声称拥有完整派生对象的安全拥有关系。

```ink
class PlainBase {
    // 没有虚函数
}

class Derived : PlainBase {
    // ...
}
```

未来拥有型容器尝试把 `Derived` 所有权擦除成 `PlainBase` 时必须产生编译错误，除非容器另外显式保存与 `Derived` 对应的完整销毁函数和存储信息。仅凭 `PlainBase*` 不能推断最派生类型。

Ink 不把“通过非虚基类销毁派生对象”定义成类似 C++ 的静默部分析构或 UB；安全语言级拥有接口必须拒绝建立这种不完整销毁关系。

## 6. 销毁与释放存储是两个步骤

动态销毁入口只负责结束对象生命周期：

```text
destroy object
    → 调用最派生析构链
    → 对象存储变为未初始化
```

它不自行猜测存储来自堆、栈、对象池、arena、共享内存还是外部分配器，也不隐式调用某个全局 `free`。

释放存储由拥有型容器保存的分配契约负责，至少需要知道：

- 原始分配地址，而不只是可能经过调整的基类子对象地址；
- 分配器或释放函数；
- 所需大小与对齐，或者能恢复这些信息的分配令牌；
- 对应模块和布局版本的有效期。

概念顺序为：

```text
dynamic destroy through vtable
    → release storage through owner allocator
```

这样栈对象、外部嵌入对象和对象池对象不会被错误地交给默认堆释放。

议题 36 的异常记录使用同样的两阶段模型。记录中的 `destroy_entry` 根据最派生异常类销毁载荷并执行完整析构链；随后由异常运行时按照该记录的分配来源释放记录存储。异常对象不需要通过自身 vptr 提供销毁入口，异常记录所引用的描述符和销毁入口已经保留了动态类型信息。

## 7. 拥有型多态容器

本议题只确定拥有型多态容器必须具备的语义，不提前确定其标准库名称和完整 API。

一个安全的拥有型基类容器必须同时保存或可恢复：

```text
基类视图地址
完整分配地址/令牌
动态销毁入口
存储释放契约
布局与模块版本
```

容器销毁时：

1. 固定对象对应模块版本；
2. 调用最派生动态销毁入口；
3. 仅在销毁完成后释放存储；
4. 清除容器状态，避免重复销毁。

Ink 当前不引入通用移动语义，因此该容器如何转移唯一所有权、是否由标准库提供固定位置句柄，留给所有权容器议题单独设计。

## 8. 接口引用

议题 26 的普通接口胖引用是非拥有借用：

```text
{ object pointer, interface table pointer }
```

它不包含存储释放权限，不能主动销毁对象。实现多个接口也不会产生多份对象所有权。

未来如果提供拥有型接口容器，该容器必须额外保存动态销毁入口和分配契约；不能仅依靠两字借用接口引用完成销毁。

## 9. 反射

用户析构函数和编译器生成的动态销毁入口默认都不作为普通反射函数公开：

- 不能通过 `type_info.function("~Entity")` 等名称找到；
- 不能通过 `FunctionInfo.call` 主动结束对象生命周期；
- `[reflect]` 不能附着到析构函数；
- 反射工具可以在类型能力信息中查询“是否需要析构”和“是否支持动态销毁”，但不能取得可随意调用的销毁方法。

需要编辑器或脚本显式释放逻辑资源时，类型作者应反射普通的 `close()`、`reset()` 等合法状态转换方法，而不是析构函数。

## 10. 热更新

动态销毁入口属于 vtable 分派 ABI，并参与模块版本固定：

- 对象必须使用与自身布局版本兼容的销毁入口；
- 旧布局对象不能由只理解新布局的销毁代码清理；
- Ink v0 布局与销毁 ABI 未变时，普通对象的 dynamic destroy 通过稳定兼容槽选择当前已发布实现；对象不会仅因由 V1 构造就固定 V1 销毁代码；
- Ink v0 遇到布局变化时拒绝 hot reload；多布局并存和显式状态迁移属于未来协议；
- 只有仍显式持有 version-local 销毁入口或表的运行时 owner 才固定旧版本；普通安全 owner 应保存稳定槽。议题 36 的活动异常记录、议题 43 的 `ExceptionBox`、活动调用、Task/frame 和固定版本的反射快照仍会按各自规则阻止旧代码卸载。

运行时不能仅按当前类型名称猜测销毁入口；它必须从已经验证 ABI/layout compatibility 的稳定分派槽选择当前实现。绕过稳定槽保存裸 version-local 地址不会自动建立 pin，在版本回收后调用属于 UB。

## 11. 异常终止与析构失败

动态销毁遵守议题 03 的普通析构规则：

- 析构函数隐式满足议题 34 的 `[nothrow]`，异常不能逃逸；
- 正常受控销毁必须执行完整析构链；
- 某层析构触发 trap 或让异常逃逸时程序立即终止，不保证继续清理剩余层；
- 崩溃、`abort` 和进程强制结束不保证执行动态销毁。

需要报告可恢复释放失败的资源必须在正常控制流中调用 `close()` 等方法。

## 12. 成本模型

每个虚类 vtable 增加一个编译器管理的动态销毁入口。对象本身不因为该入口增加第二个隐藏字段；它复用已有主 vptr。

静态已知完整类型的普通 RAII 销毁可以直接调用，不承担 vtable 查找。只有真正通过类型擦除拥有关系进行销毁时才执行动态间接调用。

普通非虚类、借用引用和原始指针不承担动态销毁状态成本。
