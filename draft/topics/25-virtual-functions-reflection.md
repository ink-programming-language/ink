# 议题 25：虚函数与动态反射调用

> 状态：已确认，2026-08-05 确认函数级 `final`；议题 26、28、34、55、57、58、60、65 与 Parser 议题 31 补充
> 确认日期：2026-08-02

## 1. 虚函数可以标记 `[reflect]`

Ink 允许把类虚函数公开到动态反射系统：

```ink
[reflect]
class Entity {
    [reflect(Category("Lifecycle"))]
    virtual func update(delta: f32) {
        // ...
    }
}

[reflect]
class Player : Entity {
    [reflect(Category("Player"))]
    override func update(delta: f32) {
        // ...
    }
}
```

`[reflect]` 控制是否生成动态函数描述符和调用适配器；`virtual` 与 `override` 控制普通语言调用的动态分派。两套机制可以组合，但语义职责不同。

本议题第 2—8、10、11 节的描述符选择、接收者检查和最终虚派发原则同时适用于同步与异步反射虚函数。同步函数使用议题 21 的 `call::<R>`；议题 57 规定异步函数使用 `call_async::<R>`，并在任务创建时进入议题 55 的虚槽任务构造 thunk。第 9 节仍只决定同步虚函数装饰器；异步函数装饰器留给后续议题。

## 2. 两阶段调用

反射虚函数调用分成两个阶段：

1. 反射查找按照议题 22 和 23，以字符串名称和子类优先规则取得一个 `FunctionInfo`；
2. 调用适配器验证接收对象和参数后，按照接收对象的动态类型执行普通虚派发。

```ink
if (match .some(type_info) = reflection.find_type("game.Entity")) {
    if (match .some(function) = type_info.function("update")) {
        const entity: Entity& = player;
        function.call::<void>(&entity, 0.016f32);
    }
}
```

即使 `function` 是 `Entity.update` 的描述符，最终也执行 `Player.update`。

反射查找决定描述符和元数据来源；虚派发决定最终执行实现。两者不能合并成“总是调用描述符声明处函数体”的直接调用。

## 3. 适配器必须通过虚槽调用

反射虚函数的编译器生成适配器必须：

- 验证接收对象至少兼容描述符的声明类型；
- 调整接收对象到正确的基类子对象地址；
- 验证参数、返回类型、引用方式和可变性；
- 通过该虚函数对应的动态分派槽进入最终实现；
- 使用调用者提供的结果存储；
- 保持议题 21 的无强制装箱和无强制堆分配规则。

适配器不能缓存或暴露某个版本原始函数体的裸地址。普通实现可以缓存虚槽索引或当前进程内句柄，但调用时仍须满足热更新和模块版本规则。

## 4. `[reflect]` 不随覆盖自动继承

一个虚函数覆盖基类方法时，不会因为基类带有 `[reflect]` 而自动生成自己的反射描述符。

```ink
[reflect]
class Entity {
    [reflect(Category("Base"))]
    virtual func update(delta: f32) {
        // ...
    }
}

[reflect]
class Player : Entity {
    override func update(delta: f32) {
        // 没有 [reflect]
    }
}
```

此时从 `Player` 反射视图查找 `update`，得到继承的 `Entity.update` 描述符及 `Category("Base")` 元数据；使用 `Player` 接收对象调用时，仍通过虚派发执行 `Player.update`。

这样不会仅因普通覆盖而隐式增加运行时反射表和元数据成本。

## 5. 子类显式反射覆盖

子类覆盖声明也添加 `[reflect]` 时，它在子类反射视图中覆盖父描述符：

```ink
[reflect]
class Player : Entity {
    [reflect(Category("Player"))]
    override func update(delta: f32) {
        // ...
    }
}
```

此时：

- `reflect(Player).function("update")` 返回 `Player.update` 描述符；
- 元数据来自 `Player.update`，不自动合并父元数据；
- 接收对象是 `Player` 的更深派生类时，调用仍继续虚派发到最具体覆盖；
- 显式取得 `Entity` 的 `TypeInfo` 仍可取得父描述符。

## 6. 其他组合

基类虚函数没有 `[reflect]`、而子类覆盖具有 `[reflect]` 时：

- 子类反射视图公开子类描述符；
- 基类反射视图不公开该函数；
- 子类描述符只能用于与子类声明类型兼容的接收对象；
- 更深层覆盖仍参与正常虚派发。

非虚反射函数不进行虚派发。子类同名反射函数只影响议题 23 的反射名称覆盖，不会仅因名称相同获得虚函数语义。

## 7. 重载、签名与覆盖检查

议题 23 禁止同一类中存在两个同名反射函数，该规则同样适用于虚函数。

`override` 必须匹配一个合法的基类虚函数，并满足语言最终确定的参数、返回类型、引用限定和调用约定兼容规则。`[reflect]` 不能放宽覆盖检查，也不能把普通同名函数变成覆盖。

议题 65 规定默认实参属于根虚槽的调用契约，不属于覆盖实现。覆盖声明不能添加、删除或改变默认值；源码直接调用先使用根槽默认表达式补全实参，再进行正常虚派发。动态反射调用始终要求完整参数，不应用默认值。

议题 55 进一步规定 `async` 是覆盖签名的一部分。同步函数不能覆盖异步虚函数，异步函数也不能覆盖同步虚函数；同步函数显式返回 `Task::<T>` 仍不等价于 `async func ... -> T`。

议题 60 规定异步虚覆盖的逻辑结果类型必须与基槽完全一致，不允许通过派生指针、接口视图或其他可转换结果形成协变。`Task::<T>` 对结果类型不变型，反射适配器也不生成结果转换任务。同步虚函数是否允许协变返回仍留给后续完整覆盖规则。

## 8. 可见性

私有或受保护虚函数可以添加 `[reflect]`。按照议题 20，这表示类型作者明确允许通过动态反射适配器调用它，但不改变普通源码可见性。

反射调用仍必须满足接收对象可变性、生命周期和模块版本要求。`[reflect]`、`virtual` 或 `override` 都不能授权访问已销毁对象或调用已卸载代码。

## 9. 同步与异步虚函数的装饰器

对本议题已经定义动态反射 ABI 的同步虚函数，虚派发选择某个最终覆盖后，进入该覆盖版本完整的装饰后实现。未被选择的基类实现及其装饰器不会因为反射描述符来自基类而额外执行。

```text
反射适配器
    → 虚派发槽
    → 最终覆盖的装饰器区域
    → 最终覆盖的原始函数体
```

派生实现显式调用基类实现时，才执行基类实现自己的装饰器链。

议题 58 对异步虚函数采用同一“最终覆盖自己的装饰器”原则，但装饰器代码位于最终覆盖的任务执行体中。任务创建时虚槽选择最终覆盖并建立其完整装饰后 coroutine frame；任务被驱动后才运行该覆盖的 `async decorator` 链。基类装饰器不沿覆盖关系自动继承，反射描述符来自基类也不会额外执行基类装饰器。

## 10. 热更新

反射描述符、反射调用适配器、虚分派槽和装饰后的最终实现必须作为同一个模块更新事务发布。

- 新调用不能观察到新描述符配旧虚槽；
- 已进入旧版本的调用可以完成；
- 旧适配器和旧虚槽在活动调用排空前不能卸载；
- 函数体地址不能作为跨更新身份保存；
- 同名匹配和重命名继续遵守议题 22。

## 11. 成本

普通非反射虚调用只承担虚分派机制本身的成本。

动态反射虚调用额外承担：

- 名称或描述符查找；
- 接收对象和参数检查；
- 一次反射适配器间接调用；
- 正常虚槽分派。

它不要求复制接收对象、建立拥有型 `Any` 或进行堆分配。编译器可以在不破坏热更新与动态类型语义时去虚拟化或内联，但不能永久绕过必须保留的更新入口。

虚类对象中的 vptr、虚槽布局和接口胖引用表示由 [`26-vtable-interface-abi.md`](./26-vtable-interface-abi.md) 规定。

接口方法的反射描述符和通过接口表执行的反射调用由 [`28-interface-reflection.md`](./28-interface-reflection.md) 规定。

普通虚调用和反射虚调用都遵守议题 34 的未检查异常规则。方法只有显式标记 `[nothrow]` 才提供不抛异常契约；覆盖方法不能削弱父方法的 `[nothrow]` 保证。

## 12. 异步虚函数的普通与反射调用

议题 55 允许类虚函数声明为 `virtual async func`。普通源码调用在创建 `Task::<T>` 时通过 vtable 选择最终覆盖，虚槽进入该覆盖的任务构造入口；异步函数体仍保持惰性，第一次 `await` 不重新查找虚槽。

已创建任务固定所选覆盖的模块版本、具体 coroutine frame、resume 和 destroy 入口。新热更新只影响以后创建的任务，不能改写已有任务的实现身份。

议题 57 允许异步虚函数显式添加 `[reflect]`。其 `FunctionInfo` 记录 `kind = async` 和逻辑结果类型 `T`；`call_async::<T>` 验证动态接收者和实参后，通过同一 vtable 任务构造槽选择最终覆盖，并把 `Task::<T>` 直接建立在调用者最终返回位置。普通 `call::<Task::<T>>` 不能替代该路径。

反射查找决定描述符与元数据来源，创建期虚派发决定最终覆盖。任务构造完成后不再保留反射参数数组，也不在第一次 `await` 时重新查找描述符或读取 vtable。

## 13. `final` 虚函数

`final` 函数修饰符封闭一个已经建立或正在建立的虚函数槽：

```ink
class Base {
    virtual func update() {
        // ...
    }
}

class Derived : Base {
    override final func update() {
        // ...
    }
}
```

派生类不能再次覆盖 `Derived.update`。`final` 不属于函数签名，不参与重载区分，也不改变参数、结果、尾随 `const` 或 `[nothrow]` 契约；它只限制后续继承层级能够提供的覆盖。

`final` 必须修饰一个虚函数槽，可以写成 `virtual final func` 或 `override final func`。普通非虚函数、`static func`、接口方法、构造函数和析构函数使用 `final` 均为语义错误。Ink 的析构函数不使用 `virtual`，动态销毁继续由议题 27 的编译器生成入口处理。

Parser 议题 31 把 `final` 与其他函数修饰符按源码顺序保存，不负责确认目标是否为虚函数，也不查询父类槽。重复修饰符和冲突组合由语义分析诊断；格式化器的规范顺序为 `virtual final func` 或 `override final func`。

`final class` 中的虚函数天然不能被更深派生类覆盖，显式再写函数级 `final` 合法但冗余。编译器可以利用最终类或最终槽去虚拟化，但仍须遵守热更新稳定入口和反射调用契约。
