# 议题 18：模块初始化、注册与清理顺序

> 状态：已确认，移除用户生命周期钩子排序；Module 议题 01 确认单文件 module，Module 议题 03 禁止实际依赖环
> 确认日期：2026-08-01

## 1. 基本原则

模块初始化遵循从依赖到使用者的顺序；模块全局对象清理遵循实际成功构造顺序的严格逆序。编译期生成的强类型注册记录随所属模块版本整体发布和撤销，不运行用户加载或卸载代码。

该规则用于：

- 普通程序启动和退出；
- 动态模块加载和卸载；
- 热更新中新版本的准备与旧版本回收；
- 新版本准备失败时的全局对象清理。

## 2. 模块依赖顺序

如果 module `A` 依赖 module `B`，则顺序为：

```text
initialize: B → A
destroy:    A → B
```

`A` 的全局对象开始初始化时，`B` 的全局初始化必须已经成功完成。销毁 `A` 的全局对象期间，`B` 及其全局对象仍然有效。

程序如果要求两个 module 具有确定先后关系，必须显式建立依赖。链接器输入、文件系统遍历和构建任务完成顺序都不构成语言语义中的依赖。

Module 议题 03 要求当前构建实际激活的依赖图是 DAG。未激活的条件导入候选边不参与本次构建顺序。

## 3. 无依赖模块

彼此之间不存在依赖路径的 module 没有语言保证的相对初始化顺序。实现可以任选确定顺序或并行准备它们，只要每个 module 发布前已经完成自身依赖和全局初始化。

程序不能通过无依赖 module 的全局初始化副作用依赖某个偶然顺序。需要顺序时应建立显式依赖；只需要并发安全时使用正常同步机制。

## 4. 同一模块内的全局对象

一个 `.ink` 文件准确形成一个 module。同一 module 中需要运行时初始化的全局对象按声明词法顺序构造，按成功构造顺序逆序析构：

```ink
var first: Resource = make_first();
var second: Resource = make_second();
```

```text
initialize: first → second
destroy:    second → first
```

第二个对象构造失败时只析构已经成功构造的第一个对象。未开始或未完成构造的对象不进入清理栈。

## 5. 注册记录顺序

强类型模块注册记录以产生它的源码声明位置作为词法锚点。不同声明生成的记录按声明顺序稳定排列；同一声明上的多个 decorator 按源码从上到下排列：

```ink
@outer
@inner
func target() {}
```

该顺序只决定静态记录的稳定枚举和冲突诊断顺序，不表示运行用户初始化代码。模块版本发布时整组记录一次性可见，撤销时整组记录一次性失效。

## 6. Decorator 调用顺序独立

注册记录顺序不改变函数调用时的 decorator 包装顺序。调用仍按：

```text
outer.before
    inner.before
        target body
    inner.after
outer.after
```

每个 decorator 可以按照议题 16 的静态 continuation 规则跳过、调用一次或调用多次下一层；这属于具体函数调用，不属于 module 初始化。

## 7. 准备失败与回滚

新 module 版本准备失败时：

- 未发布的注册记录直接丢弃；
- 已成功构造的全局对象按逆序析构；
- 旧版本的入口和注册记录保持可见；
- 不调用用户回滚或卸载钩子。

析构和运行时内部清理路径不得承担可恢复失败；触发 trap 时程序立即终止。

## 8. 动态卸载与热更新

动态卸载或旧版本回收先撤销入口和注册记录的公开状态，再等待活动使用者离开，随后逆序析构全局对象并释放代码与数据。

热更新提交把新函数实现、反射描述符和注册记录视为一个原子版本。旧版本记录的撤销不能删除同一逻辑键的新版本记录。

## 9. 并行实现

实现可以并行准备没有依赖关系的 module，但必须保证：

- 依赖者只在全部依赖准备成功后发布；
- 每个 module 内需要可观察顺序的全局初始化仍遵守词法顺序；
- 注册记录只随完整 module 版本一次性发布；
- 失败清理不破坏仍被其他已发布 module 使用的依赖；
- 所有共享状态访问遵守 Ink 的并发与内存模型。

## 10. 结论

Ink 只规定 module 全局对象、强类型注册记录和版本发布的顺序，不提供用户生命周期钩子及其排序规则。初始化从依赖到使用者，成功构造对象的清理严格逆序，注册记录随 module 版本原子发布和撤销。
