## 语法前提

以下前提来自 `grammar.bnf`，新 IR 必须保留其含义：

- Parser 不查询名称、类型或编译期结果来决定语法结构。
- 类型位置使用普通表达式，隐式要求编译期求值并产生类型值。类型注解不会使初始化表达式自动进入编译期。
- 调用和构造共用 `callee(args)`。目标是函数值时表示调用，目标是类型值时表示构造；构造目标必须是编译期已知的类型，构造参数和构造过程的阶段由所在上下文决定。
- 泛型声明使用 `[T: type, N: int32]` 等参数列表，泛型应用使用 `::[args]`。普通调用参数仍放在圆括号中。
- 语句开头的 `comptime` 覆盖紧随其后的完整语句；表达式中的 `comptime` 消费一个一元操作数，可用括号扩大范围。
- 显式 `comptime` 必须完成所要求的编译期计算，失败时报告错误，不回退为运行时执行。
- 模块和声明体在语法上可以包含语句；各位置允许的语义行为需要另外规定，语法接受不等于语义有效。

## 规则 01：IR 完整保存待处理代码

AST lowering 后，IR 必须完整保存函数体、泛型体、类型表达式、初始化表达式和编译期代码。语义分析、实例化和 comptime 不得依赖重新读取 AST 来取得延迟处理的函数体或表达式。

AST 和原始源码仍可为诊断、编辑器和源码展示保留。IR 保存源码来源，但“指向 AST 的引用”不能代替 IR 自己的代码表示。

初始 IR 允许存在未解析名称、未确定类型和依赖泛型参数的操作。完整保存代码不等于立即完成全部类型检查或求值。

## 规则 02：Operation 与 Region

采用统一的 Operation / Region 骨架，以专门的操作种类及其结构约束表达声明、应用、实例化、内存访问、控制流和编译期要求。

Region 是代码组织和处理边界，不自动等于词法作用域，也不意味着其中的代码立即执行。声明一个函数时登记函数及其函数体 Region，不执行函数体。

规则 09 进一步确定：可执行 Region 内部包含 BasicBlock，由基本块组织有序操作和控制流。共享骨架不意味着所有操作拥有相同的字段或执行行为。

## 规则 03：ValueId 与 BindingId

操作结果采用 SSA 风格的 `ValueId`：一个静态定义产生一个值身份。`ValueId` 本身不说明值的类型是否已经确定，也不说明值是否在编译期已知。

源码绑定使用独立的 `BindingId`。读取和写入绑定通过显式操作表示，不能把对变量的赋值理解为修改已有 SSA 定义。

同一循环指令可以动态执行多次，同一函数也可以多次调用；每次执行的值保存在相应环境或调用帧中，不违背静态单赋值约定。

不可变绑定可以直接关联值；需要实际存储的绑定由 Place / Load / Store 表示。此规则不要求所有局部变量立即分配内存，也不要求所有变量转换成基本块参数。

## 规则 04：名称、作用域与来源

初始 IR 用 `NameLookupOp` 保留名称查找请求，并携带 `ScopeId`、源码范围和必要的源码顺序信息。解析后引用稳定的 `BindingId` 或 `DeclId`。

需要区分：

- 名称解析：名称对应哪个声明或绑定。
- 泛型绑定：当前实例中的泛型参数取什么值。
- 执行读取：当前调用中的绑定关联什么值或存储。

名称可以已经解析，而其绑定的泛型值尚未确定。Region 的结构不能代替词法作用域信息。

具体的前向可见性、声明收集顺序和遮蔽规则尚待确定。源码中的位置范围使用 Core 的 `SourceRange`，不另建与公共诊断体系重复的容器。

## 规则 05：类型表达式与类型值

类型表达式使用普通 Operation / Region 表示，不另建一套供求值器使用的类型表达式 AST。

- 表达式求出的类型值可以通过 `ValueId` 引用。
- 具体、规范化的类型身份使用 `TypeId`。
- `TypeValue(Int32TypeId)` 表示类型 `int32`；这个值自身的类型是元类型 `type`。

例如：

```ink
let x: makeType() = value;
```

语义分析对 `makeType()` 对应的 Region 发起编译期求值，检查结果是类型值，然后用该类型分析 `value`。不因类型表达式需要编译期执行而强制执行 `value`。

指针、引用和函数类型等构造，以及 `T[N]` 的类型解释，使用相同机制。依赖尚未绑定泛型参数的类型计算可以延迟到相应实例中完成；一次实例的求值结果不能写回共享泛型模板。

## 规则 06：InstantiateOp 与 CallOp

泛型应用使用独立的 `InstantiateOp`，要求泛型实参在实例化时为编译期已知值。普通函数调用由 `CallOp` 表示。

```ink
foo::[int32, 4](value)
```

其概念过程是：

```text
求出泛型实参 int32、4
    ↓
InstantiateOp：取得 foo[int32, 4] 的实例值
    ↓
CallOp：使用普通实参 value 调用该实例
```

函数泛型的实例化结果是函数实例值；class、interface、enum 泛型的实例化结果是相应类型值。普通实参不自动成为实例键的一部分，实例化也不自动执行函数体。

泛型实例身份和缓存约束见规则 16；实例登记与递归处理见规则 17。

## 规则 07：ApplyOp 解析为调用或构造

语法中的 `callee(args)` 初始使用 `ApplyOp` 保留。语义分析确定其目标后，再准备为明确的 `CallOp` 或 `ConstructOp`。

- 函数目标：确定调用签名、参数检查和必要转换；目标可以是运行时函数值，不强制要求具体函数身份编译期已知。
- 类型目标：目标必须在编译期产生类型值，然后确定构造规则。
- 尚未确定含义的 `ApplyOp` 不直接交给执行器执行。

```ink
makeType()(value)
```

这里只强制求出构造目标 `makeType()`。外层构造以及参数 `value` 是否在编译期执行，取决于其上下文的求值要求。

## 规则 08：求值要求与值状态

Region 记录求值要求：

| 要求 | 含义 |
| --- | --- |
| `Inherit` | 继承当前执行上下文的阶段要求 |
| `ComptimeRequired` | 必须完成所要求的编译期计算 |

显式 comptime、类型表达式和泛型实参求值属于必须在编译期完成的计算。普通函数体和普通初始化表达式继承调用或所在上下文，不因“参数碰巧是常量”自动进入编译期。

`Known` / `Runtime` 等值状态保存在实例或执行环境中，不作为共享模板里某个 `ValueId` 永久不变的属性。相同普通计算操作可以服务于不同阶段。

语句形式的 `comptime` 覆盖完整后续语句。因此 `comptime if` 中被选中的执行路径也受编译期要求约束，不能只计算条件后就把选中语句中的任意运行时效果直接留下。

求值沿实际执行路径推进。显式 comptime 的实际执行需要读取运行时数据时，报告阶段错误，不回退执行。声明处理不等于执行被声明函数的函数体。

## 规则 09：Region 内使用控制流图

可执行 Region 内由 BasicBlock 和显式控制流组成。普通分支、循环、短路求值和返回使用基本块、跳转和终结操作组织。

源码 `break` 和 `continue` 分别连接到对应循环的退出块和继续块。Region、作用域及源码信息仍然保留，以支持阶段边界、生命周期和诊断。

不采用让普通 if / while 都通过嵌套 Region 的完成信号逐层传播 Return / Break / Continue 的执行模型。正常作用域退出和提前退出的清理基本块见规则 24；跨阶段边界的退出约束及 defer 的其他语义仍待确定。

## 规则 10：基本块参数

新 IR 使用基本块参数表达汇合处的 SSA 定义，跳转边携带相应实参；新 IR 不直接使用 Phi 操作。

```text
entry:
    BranchOp %condition, then_block(), else_block()

then_block:
    JumpOp merge(10)

else_block:
    JumpOp merge(20)

merge(%result: int32):
    ReturnOp %result
```

跳转时先取得全部实参，再同时绑定到目标基本块参数，避免循环回边中的参数互换被顺序赋值破坏。块参数的类型和参数数目必须与进入该块的边一致。

块参数是静态 SSA 定义，多次动态进入一个块不会创建新的静态定义。源码变量仍可通过 Binding / Place 表示，不强制全部转换为块参数。

降级到现有 InkIR 或 LLVM 时可以转换为 Phi。该选择是表示方式和接口组织的选择，不承诺固有的性能提升；多个来自同一前驱的边携带不同实参时，需要按目标 IR 的规则处理边，不能总是假定机械地逐项生成 Phi 即可。

## 规则 11：Place 与指针值

Place 表示内部的可寻址存储访问目标，通过 `ValueId` 引用，并关联元素类型、可写性等访问属性。它不是新增的 Ink 源码类型，也不要求自身是一个机器地址。

| 概念 | 含义 |
| --- | --- |
| `BindingId` | 源码中的绑定身份 |
| `Place<ptr int32>` | 指针变量自身的存储位置 |
| `ptr int32` | 可运算、传参和返回的指针值 |
| `Place<int32>` | 通过该指针访问元素的位置 |

`AddressOfOp` 从 Place 得到指针值，`DerefPlaceOp` 从指针值得到访问目标。`LoadOp` / `StoreOp` 负责实际读取和写入。成员投影和索引也可以产生 Place。

复合赋值必须复用同一次目标求值的结果。例如：

```text
%array = BindingPlaceOp B_a
%index = ReadBindingOp B_i
%slot = IndexPlaceOp %array, %index
%old = LoadOp %slot
%rhs = ReadBindingOp B_value
%new = AddOp %old, %rhs
StoreOp %slot, %new
```

指针偏移产生新指针，不直接访问目标内容：

```text
%p_slot = BindingPlaceOp B_p
%p = LoadOp %p_slot
%q = PointerOffsetOp %p, 2, element_type=int32
%dst = DerefPlaceOp %q
%value = ReadBindingOp B_value
StoreOp %dst, %value
```

`p += 2` 写回指针变量的 Place；`*p += 2` 写回被指向元素的 Place。地址和访问目标的区分不能在初始 lowering 时丢失。

元素偏移需要使用目标平台的元素步长。涉及泛型 `T` 时，先在相应实例或求值上下文中确定 `T` 及其布局。上例按 `int32` 步长为 4 字节理解；不能用宿主机器布局代替目标布局。

负偏移、指针差、比较、越界指针和尾后指针的精确规则仍待确定。`PointerDiffOp` 等名称目前仅是可能的操作分类，不据此宣布所有指针算术都已获准。数组索引原有的边界要求也不能因转为地址计算而丢失。

## 规则 12：comptime 对象内存与 LLVM 边界

comptime 执行器管理自己的对象存储；指向这些对象的指针使用分配身份与对象内字节偏移表示，不直接使用宿主机器地址。

```text
MemoryObject
{
    AllocationId
    TypeId
    Storage
    LifetimeState
    AccessPermissions
}

PointerValue
{
    AllocationId
    ByteOffset
}
```

同一 `BindingId` 在递归或多次调用中可以对应不同的 `AllocationId`。指针不能只保存 `BindingId`，否则无法区分各次调用的对象。

Load / Store 根据对象身份和偏移访问存储，并检查生命周期、访问范围和权限。对象身份机制必须避免失效指针在存储槽位复用后误指向新对象；具体 ID 编码和对象表实现尚未固定。

对象的实际 `Storage` 使用类型化数据、字节缓冲区还是混合表示，仍待确定。上述结构只确定身份与职责，也不穷举空指针、函数引用和外部符号地址的表示。

这些是解释器内部表示。运行时代码的指针降级为 LLVM `ptr`，不要求每次运行时访问也查询解释器对象表。

| 新 IR 的语义操作 | LLVM 后端的对应处理 |
| --- | --- |
| 局部存储 | 适当的局部存储表示，例如 `alloca` |
| 取地址 | 取得已分配存储或静态对象的地址 |
| 解引用形成 Place | 保存后续访问需要的地址、类型和对齐信息 |
| 指针偏移 | 按目标布局生成 GEP |
| Load / Store | 生成 load / store |

LLVM 接收完成了必要实例化、语义准备、编译期求值和结果物化的运行时代码，不直接处理未决泛型应用、类型计算或解释器 `AllocationId`。

运行时边界检查需要另外生成代码及必要元数据，不能认为解释器检查会自动出现在 LLVM 输出中。`inbounds` 也不是边界检查；只有保证满足相关条件时才能使用。具体运行时安全策略仍待确定。

## 规则 13：已知结果与结果物化

`Known(Value)` 只说明本次编译期计算已得到值，不说明该值可以作为运行时数据。

仅当计算结果需要进入运行时代码时，调用统一的物化入口：

```text
materialize(Value, ExpectedRuntimeType, Context) -> RuntimeConstant | Diagnostic
```

类型表达式的结果直接供语义分析使用，泛型实参直接供实例化服务使用，通常不需要物化成运行时数据。

| 已知结果 | 物化处理 |
| --- | --- |
| 标量 | 转换为相应运行时常量 |
| 具有按值语义的聚合 | 递归检查和转换其内容 |
| 类型值、未实例化泛型声明 | 用于编译期语义，不直接生成运行时数据 |
| 具体函数引用 | 满足运行时调用条件时转换为函数符号引用 |
| 对象指针 | 检查目标具有合法运行时存储身份，再生成对象地址 |

`StaticObjectId` 标识最终程序中的静态对象，与解释器一次执行中的 `AllocationId` 分离。物化上下文记录必要的对象映射，保证共享关系和别名关系被保留。指向已有运行时静态对象的指针应引用该对象，不复制其存储；地址可以物化不代表对象的内容可在编译期读取。

例如：

```ink
func twice(x: int32) -> int32
{
    return x * 2;
}

func main() -> int32
{
    let n: int32 = comptime twice(21);
    return n;
}
```

求值产生 `Known(Int32(42))`，物化产生整数常量 `42`，作为 `n` 的初始值。运行时执行 `main` 不需要再次执行这次 `twice(21)` 调用。

若两个编译期指针引用一个已允许导出的静态对象的不同位置，物化应得到同一 `StaticObjectId` 加各自偏移，而不是创建两份互不相关的数据。具体可导出条件受规则 14 限制。

## 规则 14：导出遵守值语义和生命周期

第一版按以下边界处理：

- 标量可以按值导出。
- 具有按值语义的数组、结构体可以递归转换内容；class 的默认值语义见规则 22，具体类型的复制、移动能力仍需另外规定。
- 按地址导出时，可以引用已有且具有合法静态存储期的对象。
- 指向编译期局部对象的指针不能通过物化自动提升为静态对象地址。
- 聚合内部包含局部对象指针时也需要拒绝，不能只检查最外层值。
- 不自动导出任意编译期对象图；显式对象固化机制尚未确定，也未新增相关源码语法。

按值返回与返回地址必须分开。例如下例按数组具有按值语义解释：

```ink
func makeValues() -> int32[3]
{
    var values: int32[3] = [10, 20, 30];
    return values;
}

func main() -> int32
{
    var a: int32[3] = comptime makeValues();
    a[0] = 99;
    return a[0];
}
```

编译期函数返回数组内容，局部数组结束生命周期。物化得到初始化常量，运行时变量 `a` 仍有自己的可变存储。各次调用的 `a` 不能变成共享可变对象。后端可以使用静态常量作为初始化模板，但必须保留此语义。

相反，下例返回局部对象地址：

```ink
func badPointer() -> ptr int32
{
    var x: int32 = 42;
    return &x;
}
```

`comptime badPointer()` 的结果不能交给运行时代码。实现可在返回处提前诊断；物化也必须拒绝这种失效对象地址。不能为使程序通过而把 `x` 自动提升为静态变量。

## 规则 15：编译期执行入口

语义分析在需要编译期结果时发起请求，以具体 Region 为入口，携带当前实例环境和执行环境：

```text
evaluateComptime(EntryRegion, InstanceEnvironment, ExecutionEnvironment) -> KnownResult | Diagnostic
```

| 输入 | 职责 |
| --- | --- |
| `EntryRegion` | 指定本次要执行的代码 |
| `InstanceEnvironment` | 提供泛型参数和必要的实例绑定 |
| `ExecutionEnvironment` | 提供当前编译期值、调用帧和对象内存 |

请求方负责结果用途的检查：类型位置要求类型值，普通初始化要求适配目标类型，泛型实参交给实例化服务。语句执行也可没有值结果；具体 Region 出口操作尚未固定。

普通函数可以在这次请求中被编译期调用，执行器为每次调用创建调用帧。函数不是仅因曾在编译期调用就永久变成某种特殊函数类别。

泛型实例化尚缺少依赖参数时，可在语义调度阶段延迟相关请求。到了必须完成求值的位置后，实际执行需要读取运行时值就是错误，不能把执行失败改写成运行时回退。

## 规则 16：语义准备、执行与实例确定性

### 16.1 按需准备操作

语义分析负责准备操作的含义、类型、重载选择和必要转换；执行器负责执行含义已确定的操作、管理控制流、调用帧和内存。

```text
取出当前操作
    ↓
语义准备：确定这次操作的含义与必要依赖
    ↓
执行已明确的操作
    ↓
保存结果，继续操作或跳转
```

类型计算可能再次提交编译期执行请求。准备沿需要的依赖和执行路径推进，不要求事先把整个泛型体的所有依赖全部求出。

“已准备”不等于“可降级 LLVM”；类型构造等操作可以是已经明确的编译期操作。未执行路径仍应接受哪些静态检查，由后续语言规则确定，不能一律省略名称和类型错误。

准备结果区分共享实例信息与单次执行信息，不能污染共享模板。依赖可变编译期值的准备结果不能无条件跨调用复用。

### 16.2 实例化、调用与代码生成分离

在固定的编译上下文中，一个完整实例键标识一个语义函数实例：

```text
InstanceKey
{
    GenericDeclarationId
    EnclosingInstanceAndRequiredComptimeCaptures
    CanonicalGenericArguments
}
```

目标平台和固定编译配置属于该上下文；跨构建缓存的依赖记录和失效机制尚待细化。不能只比较表面的泛型参数而忽略外层实例或必要捕获。

- 实例化绑定泛型参数，取得或创建函数实例。
- 编译期调用执行该实例，创建本次调用帧并得到本次结果。
- 生成运行时函数体时，泛型参数是已知值，普通参数是运行时输入。
- 普通调用的实参即使是字面量，也不隐式成为泛型参数。
- 实例缓存不等于函数调用结果缓存，不允许仅凭实例已存在就跳过一次应发生的编译期执行。

```ink
func addBias[N: int32](x: int32) -> int32
{
    let bias: int32 = comptime (N * 2);
    return x + bias;
}
```

`addBias::[3](10)` 和 `addBias::[3](20)` 复用同一实例，运行时函数体相当于 `return x + 6`。若整个调用置于 comptime，则两次调用分别得到 `16` 和 `26`，仍不创建两个函数实例。只在编译期使用的函数实例不必生成运行时函数体。

### 16.3 普通参数参与显式 comptime

```ink
func twiceCt[T: type](x: T) -> T
{
    return comptime (x + x);
}
```

- `comptime twiceCt::[int32](3)`：当前调用中的 `x` 已知，可得到 `6`。
- 普通调用 `twiceCt::[int32](3)`：生成运行时函数体时 `x` 是运行时输入，无法满足内部显式 comptime，应报告错误；不能偷偷针对实参 `3` 创建新函数。
- 若希望某个值决定实例代码，应将它显式放入泛型参数，例如 `func twiceCt[N: int32]() -> int32`。

### 16.4 共享代码的编译期依赖

决定共享运行时函数体的编译期计算，必须由泛型参数、已绑定外层环境和固定编译上下文确定。禁止读取或修改未纳入这些输入的外部可变编译期状态来决定共享函数体。

例如依赖一个每次递增的全局编译期计数器生成实例代码，会使缓存命中与处理顺序改变程序语义，不能按该方式支持。计算内部的局部变量、局部存储和循环不因此被禁止。

普通编译期调用的全部外部效果政策仍待确定。这里确定的是共享实例代码的输入约束。后端内联、克隆等优化也不改变源码层实例键的定义。

## 规则 17：实例登记、分阶段状态与递归

请求函数实例时先登记实例键和稳定的 `InstanceId`，再按需完成签名和运行时函数体。编译期执行状态属于每次调用，不存成实例唯一的“正在执行”状态。

```text
FunctionInstance
{
    InstanceId
    GenericBindings
    SignatureState
    RuntimeBodyState
}
```

| 部分 | 状态 |
| --- | --- |
| 签名 | 未处理、正在解析、就绪、失败 |
| 运行时函数体 | 未请求、正在生成、就绪、失败 |

不能用一个总的 Ready / Failed 状态替代这两个阶段。签名就绪而运行时函数体尚未生成时，编译期请求仍可按需准备和执行函数代码。

处理运行时递归的过程：

```text
登记 factorial[int32] 为 Instance7
    ↓
完成签名 (int32) -> int32
    ↓
开始生成函数体
    ↓
发现对 factorial[int32] 的递归调用
    ↓
复用 Instance7 的身份与已就绪签名，生成调用
    ↓
继续完成 Instance7 的函数体
```

调用需要目标签名，不要求目标函数体在该时刻已经生成完毕。不能因遇到正在生成的同一实例而重新创建实例或将普通递归一律报错。

编译期执行 `comptime factorial::[int32](5)` 时，各递归层复用 Instance7，但分别持有参数为 `5`、`4`、`3` 等的独立调用帧。执行不终止由规则 19 的执行预算机制处理，具体计量细节与默认值尚待确定。

规则 16 的 `twiceCt[int32]` 可以有就绪签名，但无法生成运行时函数体；这不妨碍参数已知的合法编译期调用。某一次调用的失败也不能自动污染所有其他实参的调用。共同的签名错误则仍需向依赖该签名的使用报告。

签名或类型计算中无法完成的循环依赖应报告依赖链，不能与普通函数递归混为一谈。不断产生新实例键的无限实例序列与复用同一实例的递归也是不同问题；前者受规则 20 的语义预算限制，具体计量和上限尚待确定。

## 规则 18：语义查询与依赖环

第一版采用同步的按需语义查询，以查询键和活动查询栈管理必须完成的依赖。语义查询栈与编译期函数调用栈分离。

查询键由查询种类、目标身份和必要的语义上下文组成。例如，函数签名、类型布局和运行时函数体是不同种类的查询，不能只根据目标 InstanceId 判断是否递归。

| 查询状态 | 请求处理 |
| --- | --- |
| 未处理 | 开始处理并加入活动查询栈 |
| 正在处理 | 若当前请求必须取得其尚未完成的完整结果，检查活动栈上的依赖环 |
| 已完成 | 在相同的有效查询上下文中复用结果 |
| 已失败 | 传递对应阶段的诊断，不把阶段失败扩大为整个实例不可用 |

例如：

```text
解析 A[int32] 的签名
    ↓
计算 A 的返回类型，需要调用 B
    ↓
解析 B[int32] 的签名
    ↓
又必须取得 A[int32] 尚未完成的签名
```

这条必须完成的依赖链不能推进，应报告依赖环，并附上各个请求的源码位置。语义上的相互引用不一定是这种依赖环；关键在于是否必须等待同一个尚未完成的结果。

正常递归调用取得已经完成的签名和稳定实例身份即可，不要求重新完成目标函数体；必要的函数体生成可以登记为后续任务。comptime 递归也使用独立调用帧，不因同一个 InstanceId 多次出现在函数调用栈上而报告语义依赖环。

结果复用适用于输入确定的语义查询，不把普通编译期函数调用一律视为可缓存查询，不据此跳过应发生的执行或副作用。执行预算及其资源错误见规则 19；跨构建缓存和任意调用结果缓存仍待确定。

## 规则 19：编译期执行预算

一次根编译期执行请求拥有一个执行预算上下文。内部函数调用、循环，以及语义准备再次触发的嵌套编译期执行共享该上下文；进入新的调用帧或重新进入执行入口不能重置剩余预算。

```text
根请求：comptime buildTable()
    ├─ 执行循环
    ├─ 调用 makeRow()
    └─ 语义准备触发嵌套 comptime 求值

上述执行共享同一预算上下文
```

分别限制以下资源：

| 限制 | 作用 |
| --- | --- |
| 可执行操作步数 | 限制持续计算，包括不递归的无限循环 |
| 调用深度 | 限制过深的递归执行 |
| 解释器管理的内存用量 | 限制巨大分配或持续创建对象 |

仅限制调用深度不能处理无限循环，仅限制步数也不能约束一次巨大分配。具体计量规则、默认上限和配置接口留待实现时确定。

超过预算时终止本次请求并报告资源限制诊断，附上根请求位置及当前调用链。不能产生伪造的 Known 结果，也不能回退成运行时执行。

资源限制不等于已经证明函数语义非法，不能永久缓存为该实例在任何预算下都失败。提高限额后可以重新发起请求，但不自动重试有副作用的执行，也不因此承诺回滚任意副作用。失败状态清理与外部效果政策仍需单独设计。

本条确定编译期执行的预算机制。泛型实例与语义查询的增长由规则 20 另外限制，整个编译会话的其他总资源限制和取消机制仍需另行约定。

## 规则 20：语义分析预算

编译会话单独设置语义分析预算，覆盖同步查询以及登记到工作队列的后续函数体生成任务。这些工作不能仅靠 comptime 执行器计步限制。

| 限制 | 作用 |
| --- | --- |
| 新增泛型实例数 | 控制不断产生不同实例 |
| 语义查询处理量 | 控制持续展开的分析工作 |
| 生成的 IR 规模 | 控制代码和相关数据膨胀 |

例如：

```ink
func grow[T: type]() -> void
{
    grow::[ptr T]();
    return;
}
```

从生成 `grow[int32]` 的运行时函数体开始，会继续请求 `grow[ptr int32]`、`grow[ptr ptr int32]` 等不同实例。每次实例键都不同，活动查询栈上没有重复键；延后生成函数体也只会把增长转移到工作队列，不能靠循环检测保证终止。

复用已存在的实例时不重复扣除新增实例额度。后续排队任务继续受同一会话预算约束，并保留根请求、触发位置等来源信息，超限时能够报告当前触发的实例链。

语义预算超限属于资源限制，不能把超限当作已经证明存在无限递归，也不能将受影响模板永久标记为语义非法。有限但规模很大的程序也可能超限，允许提高限额后重新编译。

本条与规则 19 分别管理语义展开和编译期函数执行的资源。具体默认值、查询工作量和 IR 规模的计量方式、会话实现与取消机制仍待确定。

## 规则 21：类型身份、成员信息与布局

声明型类型先登记稳定身份，再分别按需准备成员信息和计算目标内存布局。取得 TypeId 不要求类型的全部成员及布局已经完成，也不意味着该类型一定具有运行时存储表示。

对于泛型声明型类型，身份绑定其完整实例环境。成员信息和布局的准备状态分开记录；布局查询需要明确目标上下文。具体记录字段仍是实现细节。

| 信息 | 职责 |
| --- | --- |
| 类型身份 | 标识哪个类型，支持类型引用和泛型参数绑定 |
| 成员信息 | 提供字段、方法及其类型或签名 |
| 内存布局 | 提供对象大小、对齐、字段偏移等存储信息 |

例如，在解析下列类型的成员之前先登记 Node 的身份，使类型体中的自引用能够指向同一个 TypeId：

```ink
class Node
{
    class_field value: int32;
    class_field next: ptr Node;
}
```

构造 `ptr Node` 只要求 Node 的类型身份。指针本身的布局由目标平台决定，不需要先求出 Node 本体的完整尺寸；真正为 Node 对象安排存储时再请求相应布局。

按元素偏移一个 `ptr Node` 时需要 Node 的元素步长，不能把“指针可表示”扩大成“所有指针操作都无需目标布局”。成员查找与取得成员的存储偏移也需要区分各自的依赖。

若某个类型采用直接内嵌字段的存储表示，布局计算又必须依赖它自身尚未完成的布局，则应报告按值布局依赖环。class 的默认值语义见规则 22；本条不一概放开其他名称的前向可见性。

匿名结构类型的等价规则、具体对象 ABI 与布局算法仍待确定。

## 规则 22：class 默认值语义

class 默认表示对象值，普通 `T` 变量和按值字段具有对象自身的存储语义；需要访问或共享既有对象时显式使用 `ptr T`、`ref T` 等间接表示。具体引用绑定和所有权规则不由本条确定。

例如，假设 Point 仅包含两个数值字段并允许复制，`makePoint()` 返回已初始化的 Point。在函数体内：

```ink
var a: Point = makePoint();
var b: Point = a;
b.x = 10;
```

`a` 和 `b` 是独立对象，修改 `b` 自身的普通数值字段不会修改 `a` 的对应字段。复制指针字段只复制指针值，两个指针仍可能指向同一对象，不自动复制其指向的整个对象图。

普通 `T` 字段按其值表示内嵌到所属对象中。直接或间接形成无限按值包含的布局需要报错，例如：

```ink
class Bad
{
    class_field next: Bad;
}
```

通过 `ptr T` 形成递归对象关系不会要求无限内嵌存储，规则 21 中的 Node 因此可以先建立类型身份，再完成其有限布局。

值语义不意味着所有类都必须可复制，也不意味着复制、移动、构造和析构都可以降为原始字节操作；这些能力和操作的选择还需分别规定。

后端可根据目标 ABI 和优化需要采用寄存器、栈存储或地址传递，只要保持源语言的对象独立性与其他可观察行为。按值语义不承诺固定的物理传参形式。

继承下的转换、切片、多态销毁、复制或移动能力及接口表示仍待确定。

## 规则 23：对象生命周期操作

IR 分别表达存储取得、对象初始化、已有对象赋值、对象销毁及存储结束，不能将这些行为一律表示为普通 StoreOp。

| 行为 | IR 职责 |
| --- | --- |
| 取得存储 | 准备可承载对象的存储或抽象位置 |
| InitOp | 在目标存储中建立对象，例如带初始化表达式的局部绑定 |
| AssignOp | 按类型规则给已有对象赋值，不默认等价于销毁后重新初始化 |
| DestroyOp | 执行对象生命周期结束所需的销毁行为 |
| 结束存储 | 结束或释放承载对象的存储，与对象销毁分开 |

概念流程：

```text
%a = LocalStorageOp T
InitOp %a, %initial
AssignOp %a, %source

// 到达需要销毁对象的清理点
DestroyOp %a
EndStorageOp %a
```

LoadOp / StoreOp 保留为基础内存访问。语义准备确定初始化、赋值和销毁的具体行为后，才能判断是否可以降为这些基础操作。简单类型的相关行为可以简化为普通读写，非平凡对象需要执行其类型规定的相应动作。

此分离同样适用于 comptime 和运行时，不能让解释器直接复制存储而跳过对象行为。销毁对象也不等同于释放承载存储。

IR 保留足够的来源信息供后续确定复制或移动等初始化方式。本条不规定所有类型都可复制，不新增特殊成员函数的源码语法，也不把语义伪代码中的中间结果固定为必须存在的临时对象；可以在满足语义时直接在最终目标位置构造。

作用域清理顺序和正常控制转移的清理边见规则 24。具体的初始化状态检查、部分初始化失败处理和 defer 的求值方式仍待确定。

## 规则 24：作用域清理与控制流

按作用域登记清理义务，自动对象销毁和执行到的 defer 共同按登记顺序的逆序执行。对象完成初始化后才产生相应的销毁义务；未执行到的 defer 不产生清理义务。

正常离开作用域以及 return、break、continue 等合法控制转移，通过显式清理基本块执行所退出作用域的清理动作。只清理本次实际退出的作用域，不能提前销毁仍然有效的外层对象。例如，continue 需要清理本轮循环体内的对象，但不能销毁循环外仍有效的对象。

例如：

```ink
func work() -> int32
{
    var a: Resource = makeResource();
    defer finish();
    {
        var b: Resource = makeResource();
        return 1;
    }
}
```

假设 Resource 需要销毁，登记顺序为 a 的销毁、finish、b 的销毁。返回过程为：

```text
先求出返回值 1
    ↓
销毁 b
    ↓
执行 finish()
    ↓
销毁 a
    ↓
返回之前保存的结果
```

先求出并保存返回结果，再进入清理块，最后执行 ReturnOp；基本块参数可携带返回值。对象销毁与相应存储结束仍遵守规则 23 的分离。

清理栈描述语义上的登记和生成顺序，不强制最终程序维护通用的动态清理栈。条件路径上的清理义务可通过相应控制流或必要状态表达；不同有效清理集合不能无条件共用同一串销毁动作。

本条确定正常执行和合法控制转移的清理行为。defer 表达式的捕获或实参求值时机、部分初始化失败、返回对象的复制或移动方式及跨阶段退出合法性仍待确定。编译器诊断、取消和预算耗尽时的内部资源释放也不等同于执行用户的 defer，相关失败处理另行设计。

## 模块职责与处理关系

| 模块职责 | 输入与输出 |
| --- | --- |
| AST lowering | 从语法 AST 建立完整的新 IR，保留来源和作用域关联 |
| 语义分析与准备 | 解析名称、类型、应用和转换，发起必要求值及实例化请求 |
| 实例化服务 | 规范化实例参数，登记身份，管理签名和运行时函数体状态 |
| comptime 执行器 | 按需协作准备并执行 Region，管理调用帧和对象内存 |
| 结果物化 | 检查可导出性，产生运行时常量及合法静态对象引用 |
| LLVM 后端 | 接收完成必要语义处理的运行时代码，生成目标 IR |

```text
源码 → Tokenizer → Parser → AST
                           ↓
                    完整的待处理 IR
                           ↓
                 语义分析 / 实例化服务
                           ↕ 按需求值与准备
                     comptime 执行器
                           ↓ 需要进入运行时的已知结果
                        结果物化
                           ↓ 与剩余运行时代码汇合
                  已完成必要语义处理的运行时 IR
                           ↓
                         LLVM
```

上图描述职责与依赖关系，不要求建立多套相互重复的 IR 数据结构，也不表示每个阶段都是只能执行一次的整模块线性 pass。

## 当前讨论：规则 25 提案（待确认）

建议 defer 延迟其后完整表达式、赋值或块的执行，在作用域清理到该项时才求值。登记时只建立清理义务，不立即计算调用目标、实参或赋值目标，也不默认保存变量值的快照。

名称按 defer 所在的词法作用域及既定可见性规则解析到稳定的 DeclId / BindingId；清理时读取这些绑定当时的值，不在退出时重新按名称查找。此规则不放开尚未确定的前向可见性，也不允许读取已经失效的对象。

例如，在函数体中：

```ink
var x: int32 = 1;
defer record(x);
x = 2;
```

退出作用域时调用 `record(2)`。若希望保存登记时的数值，可以显式创建独立绑定：

```ink
var x: int32 = 1;
let saved: int32 = x;
defer record(saved);
x = 2;
```

该例退出时调用 `record(1)`。数值保存来自显式初始化 saved，而不是 defer 自动捕获快照。

这使 `defer call(args);`、`defer target = value;` 与 `defer { ... }` 具有一致的延迟执行含义。IR 在对应清理代码中保留完整求值过程，而不是在登记点提前生成参数的求值。

本条不决定 defer 内部的 return / break / continue、注册新的 defer 或跨阶段控制转移是否合法，亦不决定所有权捕获等额外机制。确认前不计入已确认的 24 条规则。
