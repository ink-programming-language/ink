# VM 运行时设计讨论稿

本文讨论 Ink 底层虚拟机的执行状态、栈和调用约定，作为重新设计指令的依据。下文区分已确认的方向与补充建议；建议部分尚未成为固定 ABI，也不表示运行时已经实现。

## 已确认的方向

1. VM 提供 `pc`、`bp`、`sp` 三个逻辑寄存器。
2. 函数参数通过栈传递。
3. 栈空间通过支持寄存器操作数的 `add` 指令调整 `sp`，基本状态变化为 `sp := sp + x`。

逻辑寄存器属于 VM 的可见执行状态，与宿主 CPU 的寄存器分配无关。解释器计算有效地址、解码操作数时使用的宿主临时变量不增加 VM 的逻辑寄存器。

## 寄存器和栈：建议约定

建议以字节为地址、偏移和长度的单位，栈向高地址增长，`sp` 指向栈顶之后的首个空闲字节。

| 寄存器 | 建议含义 |
| --- | --- |
| `pc` | 当前指令起始位置；顺序执行成功后移至下一条指令，分支、调用和返回显式改变它。 |
| `bp` | 当前函数栈帧的固定基址；函数体内预留临时空间或准备下一次调用时保持稳定。 |
| `sp` | 当前有效栈空间的末端；有效区间为 `[StackBegin, sp)`，可用容量为 `[sp, StackEnd)`。 |

当前对象格式只接受 64 位地址，初版运行时可以沿用这一宽度，`bp` 和 `sp` 使用完整的 64 位寄存器操作。`pc` 的写入仅由控制转移指令完成。VM 地址的数值表示不直接暴露宿主指针；宿主栈缓冲区增长或移动时，已经形成的 VM 栈地址仍应保持有效。

每次调用拥有独立的帧，因此递归调用不会覆盖上一层调用的参数和局部变量。函数内的长期槽位建议使用 `bp + 固定偏移` 访问，短期的调用准备区可以使用 `sp` 相对寻址。

## 栈空间调整：建议约定

以 `sp` 为目标的寄存器加法直接调整栈顶。下例中的 `rri` 按目标、左来源、右来源的顺序表示两个寄存器操作数和一个立即数操作数：

```text
add64rri sp, sp, 16     // 预留 16 字节
add64rri sp, sp, -16    // 回收 16 字节
```

建议写入 `sp` 时将来源立即数按有符号字节增量解释。正增量预留空间，负增量回收空间，零增量保持栈顶不变。预留的空间不初始化；回收的空间不再属于有效栈空间。

执行前按数学意义计算新的地址，检查地址计算没有溢出，且新栈顶位于 `[StackBegin, StackEnd]` 内；通过检查后一次性更新 `sp`。普通栈调整还应保持当前活动帧和调用保存区有效，具体可回收边界仍需在调用约定中确定。失败通过显式 trap 报告，`sp` 保持原值。

这一规则适用于所有写入 `sp` 的指令。普通整数 `add` 仍按指定位宽回绕；更新栈顶不能先回绕，再只检查最终数值是否位于栈范围内。

函数返回时回收整个函数帧中的局部空间。函数内提前回收空间时，执行该调整的函数须保证已回收空间不再被使用。

建议按增量精确移动栈顶，不暗中取整。槽位间的对齐填充由布局方计入调整量，调用边界的对齐也由调用方保证。

## 函数调用与返回：建议约定

建议参数按声明顺序从低地址向高地址排列。调用方先为返回值和全部参数预留一块调用区，再写入参数；被调用方通过自己的 `bp` 和固定偏移读取参数。参数按值传递；引用参数在栈上存放地址值，具体参数大小和对齐由函数签名及其布局规则决定。

返回值也建议通过栈传递：调用方在参数区之前预留结果槽，被调用方在返回前写入该槽。无返回值的函数不需要结果槽。这一方案可以承载标量或聚合结果，无需新增返回值寄存器。

建议调用过程在调用区之后保存旧 `bp` 和返回 `pc`，并将新 `bp` 指向这段保存区的起点。以 64 位地址和两个 8 字节保存项为例，帧形状如下：

```text
低地址
┌────────────────────────────┐
│ 调用方已有的帧空间         │
├────────────────────────────┤ ← CallBegin
│ 返回值槽及对齐填充         │
│ 参数 0、参数 1、……及填充   │
├────────────────────────────┤ ← bp（进入被调用方后）
│ 旧 bp                      │  bp + 0
│ 返回 pc                    │  bp + 8
├────────────────────────────┤ ← bp + 16
│ 被调用方局部变量、临时空间 │
├────────────────────────────┤ ← sp
│ 尚未使用的栈容量           │
└────────────────────────────┘
高地址
```

初版可以建议调用边界按 8 字节对齐；更大对齐、聚合布局和可变参数规则仍需另行确定。返回槽与参数的偏移由调用双方使用相同的签名布局计算，不依赖运行时逐个压栈的顺序。

建议的状态转换如下：

1. 调用方记录 `CallBegin = sp`，预留返回槽、参数及填充，并写入参数。此时 `sp` 位于调用区末端。
2. 调用操作验证目标和保存区容量，将旧 `bp`、下一条指令地址 `NextPC` 写入保存区，然后设置 `bp = 原 sp`、`sp = bp + 16`、`pc = 函数入口`。
3. 被调用方通过寄存器形式的 `add` 增加 `sp`，预留局部空间，使用稳定的 `bp` 定位参数和局部变量；它也可以继续准备嵌套调用。
4. 返回前，被调用方完成结果槽写入，并读取保存的旧 `bp`、返回 `pc`。返回操作将 `sp` 恢复为当前 `bp`，再恢复旧 `bp` 和返回 `pc`，由此回收保存区及全部局部空间。
5. 调用方读取或转存结果，再将 `sp` 恢复到 `CallBegin`，回收参数和结果槽。调用方须能通过自身帧布局重新定位 `CallBegin`，不能依赖调用过程保留宿主临时变量。

这一方案由被调用方回收自己的保存区和局部空间，由调用方回收调用区。栈上对象的地址可以在其存活期间传递给下一层调用；函数返回后，属于其已回收帧的地址失效，不能作为有效结果交给调用方使用。

### 两个参数和一个结果的示例

假设某函数接收两个 64 位整数并返回一个 64 位整数，调用方原先 `sp = 1024`。返回槽和两个参数依次占据：

| 区间 | 内容 | 进入被调用方后的地址 |
| --- | --- | --- |
| `[1024, 1032)` | 返回值 | `bp - 24` |
| `[1032, 1040)` | 第一个参数 | `bp - 16` |
| `[1040, 1048)` | 第二个参数 | `bp - 8` |
| `[1048, 1056)` | 旧 bp | `bp + 0` |
| `[1056, 1064)` | 返回 pc | `bp + 8` |

准备参数后 `sp = 1048`。进入函数后 `bp = 1048`、`sp = 1064`；执行 `add64rri sp, sp, 16` 后 `sp = 1080`，局部空间为 `[1064, 1080)`。返回后旧 `bp` 和返回 `pc` 已恢复，`sp = 1048`；调用方取得 `[1024, 1032)` 中的结果后，执行 `add64rri sp, sp, -24`，将 `sp` 恢复为 `1024`。

## 执行边界与失败：建议约定

`pc` 必须指向合法指令起点。解码需要验证操作码、操作数长度以及目标指令边界；普通指令成功后执行 `pc = NextPC`，调用保存的也是 `NextPC`。程序入口可以使用专用的初始调用帧，最外层返回结束执行，不将任意地址当作退出哨兵。

栈容量不足、地址运算溢出、非法访存、非法指令和无效跳转目标建议通过 VM 的显式执行结果或 trap 状态报告。trap 是 VM 的停止状态，不使用宿主 C++ 异常；失败前完成必要检查，避免只更新一部分寄存器或调用帧。退出值和错误信息的对外接口仍待运行时 API 设计确定。

对象文件验证与执行验证分开处理。现有对象读写搬运原始代码字节，对象结构验证成功不代表代码已经完成指令边界、调用约定或访存验证。
