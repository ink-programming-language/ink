# VM 运行时设计讨论稿

本文记录 Ink 底层虚拟机的执行状态、已实现的最小分派循环和后续栈操作规划。函数调用布局单独记录在 [VM 调用约定](VM-Calling-Convention.md)；标为建议的约定仍需后续执行器支持。

## 已确认的方向

1. VM 提供 `pc`、`bp`、`sp` 三个地址寄存器，以及恒零的 `zero` 寄存器。
2. 函数参数通过栈传递。
3. 栈空间通过支持寄存器操作数的 `add` 指令调整 `sp`，基本状态变化为 `sp := sp + x`。

逻辑寄存器属于 VM 的可见执行状态，与宿主 CPU 的寄存器分配无关。解释器计算有效地址、解码操作数时使用的宿主临时变量不增加 VM 的逻辑寄存器。

[VM 内存模型与指令构建](VM-Module.md) 提供逻辑模块与指令构建，[模块链接器](VM-Linker.md) 合并模块并绑定可见定义，未满足的声明留待加载解析。镜像布局、发射与加载已实现；解释器支持部分 Add、Load、Store、四种无条件跳转、显式比较分支、地址型 `Calli`、内存间接 `Callm` 以及普通和最外层 `Ret`，其余指令执行仍待实现。

`vm_runtime` 和 `runtime_stub` 分别构建为独立静态库 `ink_vm_runtime`（`ink::vm_runtime`）和 `ink_runtime_stub`（`ink::runtime_stub`）。前者提供 `NativeSymbolAddresses` 并链接后者，后者提供通用 Native 桩并链接共享 C Runtime `ink::runtime`；依赖链为 `ink::vm → ink::vm_runtime → ink::runtime_stub → ink::runtime`。

`runtime_stub/windows` 仅在 CMake 的 `WIN32` 目标上加入，构建独立平台库 `ink_runtime_stub_windows`（`ink::runtime_stub_windows`）。Windows 上的 `ink::runtime_stub` 链接该平台库，平台库链接 `kernel32`；其他目标不编译或链接 Windows 桩。

`Interpreter` 持有诊断引擎和 Loader。`initialize()` 以 `try_emplace` 将 `NativeSymbolAddresses` 登记到统一 `ExportSymbolMap`，同时将 stub 地址加入 hash set。重复初始化保留已有同名绑定。名称查询只查统一符号表；`Calli` 和 `Callm` 按最终地址查询 stub 集合，同名 Ink 导出覆盖不会把它误判为 stub。

解释器还持有当前 `Frame`。首次 `initialize()` 预留初始代码段容量，并读取 `config.def` 中的 `VMStackBytes`，用 `malloc` 创建一次栈分配。默认大小为 2 MiB（2097152 字节），可通过 `INK_VM_STACK_BYTES` 环境变量覆盖，无效的十进制值或溢出值使用默认大小；零字节配置不分配栈存储。构造后的寄存器保留 `Frame` 默认状态，BP、SP、PC 的整数值均为 0。重复 `initialize()` 注册 Native 符号并保留当前帧与当前栈，不重新读取配置或重置寄存器。

`Interpreter::execute(const void *Entry)` 接受已加载代码段中的宿主入口地址。入口不在有效代码字节范围内或不满足八字节对齐时报告 `VMExecutionFailed`（`INK-V0005`），返回 `false` 并保留此前帧和栈。有效入口会重置当前帧并复用初始化时创建的栈：栈向高地址增长，BP、SP 均保存原始栈分配的起始地址，PC 保存 `Entry` 的地址，ZERO 恒为 0；零字节栈的 BP、SP 为 0。每次有效入口执行都重置这些寄存器，保留栈分配与其中的字节，随后调用单独定义于 `dispatch.cpp` 的私有 `dispatch()`。

`getFrame()` 返回当前帧，BP、SP、PC 均以 u64 保存宿主地址，ZERO 恒为零。READ/WRITE 宏读取或更新整数寄存器，GET/SET 宏提供寄存器存储的字节视图。帧复制重新绑定自身寄存器存储。解释器保留原始栈分配及大小，用于 CALL/RET 的栈边界检查，修改 BP 或 SP 不影响原始分配的释放。栈存储在解释器生命周期内保持稳定。

`Frame::getPC()` 和 `setPC()` 直接访问 `Register[PC]` 绑定的同一个 PC 存储，不增加字段或局部缓存；通过 READ/WRITE 或 GET/SET 修改该存储后，直接访问器立即看到更新。分派每轮读取当前 PC 并将其作为指令地址，各 handler 的指令长度由 opcode traits 在编译期确定；开启断言时仍完整验证动态编码长度、对齐、保留位及寄存器编号。

当前分派循环读取八字节对齐的头字，从低 16 位提取 opcode，从其后三个字节提取寄存器编号。六种已实现的 64 位 Add 形式均读取三个八字节操作数槽，并通过 `READ_REGISTER` 从 `Frame` 寄存器存储读取值；ZERO 恒为 0。`r` 来源为寄存器值加偏移位模式，`m` 来源在同样计算有效地址后，再从该地址读取八字节内存值。加法按 64 位位模式回绕；`Add64rrr`、`Add64rrm` 和 `Add64rri` 更新寄存器目标，`Add64mrr`、`Add64mmi` 和 `Add64mmm` 更新内存目标。每条指令均将 PC 前进 32 字节继续分派。指令编码的对齐不要求数据有效地址对齐，内存来源与目标仍按字节复制，来源在目标写入前完整读取。

调用方须提供完整有效的指令编码及有效访存地址。分派通过 `check` 表达头部、指令长度和寄存器编号的内部前置条件。`Calli`、`Callm` 和普通返回在提交状态前通过 `check` 检查代码目标范围与八字节对齐、栈寄存器和返回帧结构；CALL 保存区容量不足与递归超限通过 `REPORT_IF` 报告 `VMExecutionFailed` 并返回 `false`。最外层 `Ret` 成功结束执行并将 PC 保留在该指令。已知但未实现的 opcode 同样报告执行失败。完整指令边界、数据权限和一般访存验证仍属后续工作。

`CodeWords` 使用 `std::vector<std::uint64_t>` 拥有完整整数槽，`CodeSegment` 是同一存储的字节视图；指令直接按整数槽读取，数据访问保留按字节复制。解释器另存逻辑有效字节数和按八字节取整的容量。`getCodeSegment()` 返回覆盖有效字节的 `std::span<const std::uint8_t>`，`getCodeSegmentCapacity()` 返回分配容量。容量不足时通常倍增并向上取整，创建新的整数槽数组，复制覆盖有效字节的完整槽，再安装新存储并修补既有宿主地址。尾槽的额外字节不计入逻辑有效长度。

只要代码段地址改变，解释器就将统一符号表中指向旧代码段的地址平移到新存储，并遍历既有库的两类地址重定位修补字段。动态重定位从字段中读取原绑定值并逆向去掉 `Addend` 后，才能判断原符号基地址是否位于旧代码段；属于旧代码段时换算到新基址，再加回 `Addend`，Native 地址保持不变。该过程保留旧引用已经选择的目标，不按最新同名导出重新解析，因而后续符号覆盖不会改变旧库的绑定。镜像基址重定位则直接根据各库的新宿主基址、`TargetOffset` 和有符号 `Addend` 重算，不读取旧绑定值、不查询统一符号表。原始 `ExecutableFile::Image` 和重定位记录不参与改写。

`Interpreter::loadLibrary(ExecutableFile)` 先确保容量并完成必要的既有地址修补，再创建 RAII 加载事务。事务保存此时的符号表、有效字节数和下一个 handle，为非空镜像将起点向上对齐到八字节，清零库间填充后追加原始 `Image`，调用接收可写 `std::span<std::uint8_t>` 的 `Loader::loadLibrary(CodeSegment, ImageBase, ExecutableFile &)`；`ImageBase` 是插入对齐填充后的镜像起点；空镜像不额外插入填充。Loader 先登记本库导出，再解析导入和修补地址，成功后提交事务。找不到符号地址时报告 `VMLibraryLinkFailed` 并返回 `false`，事务恢复符号表、有效字节数和 handle 计数，并删除新增库记录，解释器返回 0。已完成的容量增长和存储搬迁保留，既有有效字节中的非地址内容不变，内部符号地址及旧重定位字段与当前存储保持一致；失败不保证恢复原容量、原存储地址或地址字段的旧位模式。内部不变量失败会报告 ICE 并终止进程，不经过事务析构回滚。

成功的 `uint32_t` handle 从 1 开始且不复用，普通链接失败不消耗 handle；handle 空间耗尽也返回 0。handle 映射到包含 `ImageBase` 和 `ExecutableFile` 的 `LibraryDescriptor`，`findExecutable` 对未知 handle 返回 nullptr，已有文件的借用指针保持有效。代码段 span 及通过符号表取得的裸地址可能在后续加载尝试扩容搬迁时失效，即使该次加载最终因缺少符号而失败；调用方应在加载尝试后重新取得 view 和查询地址。当前搬迁修补只维护解释器内部登记的地址，不更新调用方自行保存的指针。

`tools/interpreter` 中的 `ink-interpreter` 工具持有解释器实例，将输入文件原始字节读入 `ExecutableFile::Image` 后调用 `loadLibrary`，输入为 `-` 时读取标准输入。可执行文件解码器尚未实现，此时不读取入口、导入或重定位元数据。Loader 在导出循环中检查偏移，将 `CodeSegment.data() + ImageBase + Export.Offset` 对应的宿主地址写入统一符号表；同名导出覆盖当前绑定，因此本库导入也能查到本库导出。随后为完整导入表中的每项调用一次 `Interpreter::resolveSymbolAddress(Name)` 并按索引缓存地址，再遍历 `DynamicImportSymbolRelocations`，加上有符号 `Addend` 后直接通过 `uint64_t *` 写入目标字段，不构造修补数组。同次加载也绑定 `ImageBaseAddressRelocations`：将 `CodeSegment.data() + ImageBase + TargetOffset` 的宿主地址加上有符号 `Addend` 后写入字段。本表固定引用当前镜像，不查询统一符号表，也不参与同名符号覆盖；`TargetOffset` 可等于镜像字节数，表示 one-past 位置，但字段本身必须完整位于镜像内。

直接地址写入要求小端宿主及实际字段八字节对齐，违反镜像和重定位内部不变量会报告 ICE。原始 `ExecutableFile` 保持未绑定，所有写入只作用于运行时副本。Loader 对调用地址使用同样的重定位规则，不改写调用 opcode。

## 寄存器与符号操作数

`register.def` 通过 `REGISTER(Kind, Encoding, Spelling)` 定义寄存器，`register.h` 据此提供底层类型为 `std::uint8_t` 的 `RegisterId`：

| 寄存器 | `RegisterId` | 编号 | 文本名称 |
| --- | --- | --- | --- |
| 帧基址 | `BP` | `0` | `bp` |
| 栈顶 | `SP` | `1` | `sp` |
| 程序计数器 | `PC` | `2` | `pc` |
| 恒零基址 | `ZERO` | `3` | `zero` |

寄存器值使用上述独立编号，符号引用通过 `core::Name` 保存链接名，文本用 `@name` 或 `@"escaped name"` 标识符号。

寄存器来源保存编号和有符号偏移，值为寄存器值加偏移，不读取目标内存；地址来源在此基础上读取内存。符号内存地址统一采用 ZERO 基址加加载时填写的地址字段，本镜像符号使用镜像基址重定位，外部符号使用动态导入重定位。基本块目标及 `Jmpi` 仍保留 PC 相对位移。

VM 与其他 Ink 组件统一使用 `InkVersion`，默认 `0.0.1`。指令集包含加载、存储、ADD、四种无条件跳转、显式比较条件跳转、RET，以及统一 `call` 的立即数与内存形式，详见 [VM 指令编码格式](VM-Instruction-Format.md)。

## 无条件跳转

以下四种无条件跳转成功后直接将 PC 改为目标地址，不再执行顺序后继。四种形式如下：

| 操作码 | 文本 | 目标来源 | 总长度 |
| --- | --- | --- | --- |
| `Jmp` | `jmp done` | 同一函数中的目标基本块；发射为 PC 相对地址 | 16 字节 |
| `Jmpi` | `jmpi 16` 或 `jmpi @target` | 当前指令起始 PC 加有符号 64 位立即位移 | 16 字节 |
| `Jmpr` | `jmpr pc + 16` | 寄存器值加有符号字节偏移 | 16 字节 |
| `Jmpm` | `jmpm [bp + 8]` | 从有效地址读取八字节目标宿主地址 | 16 字节 |

`Jmp` 借用同函数基本块指针；`Jmpi` 的符号目标必须为已定义 VM 函数，按 PC 相对形式解析，addend 必须为零。`Jmpr` 使用寄存器值，`Jmpm` 从指针槽读取目标；槽内地址才是跳转目标。

## 显式比较条件跳转

条件跳转在一条指令内读取两个来源、进行比较并选择目标，不保存标志或其他隐式比较状态。文本例如：

```text
je64mib [bp + 16], 42, equal
jlt64mmb [bp + 16], [bp + 24], signed_less
jltu64mib [bp + 16], 42, unsigned_less
```

支持 `je`、`jne`，有符号关系 `jlt/jle/jgt/jge`，以及无符号关系 `jltu/jleu/jgtu/jgeu`。每种关系提供 8、16、32、64 位比较及 `mmb`、`mib` 两种形式，共 80 种操作码。`mmb` 从两处内存各读取指定位宽的值；`mib` 从内存读取左值，并将八字节立即数槽的对应低位作为右值；窄立即数编码时零扩展。相等比较按位判断，有符号比较按相应位宽的二进制补码解释。

目标块始终位于第三个操作数。条件成立时 PC 转移到目标块；否则 PC 前进到整条比较分支之后。目标位移相对当前指令起始 PC，比较不会写入任何寄存器或内存，PC 除外。比较来源、位宽和关系由 opcode 固定，不增加运行时操作数类型或 ZERO 判断。目标只接受同一函数中的块；需要间接条件转移时，让目标块执行已有的 `jmpr` 或 `jmpm`。

## 寄存器和栈：建议约定

建议以字节为地址、偏移和长度的单位，栈向高地址增长，`sp` 指向栈顶之后的首个空闲字节。

| 寄存器 | 建议含义 |
| --- | --- |
| `pc` | 当前指令起始位置；顺序执行成功后移至下一条指令，分支、调用和返回显式改变它。 |
| `bp` | 当前函数栈帧的固定基址；函数体内预留临时空间或准备下一次调用时保持稳定。 |
| `sp` | 当前有效栈空间的末端；有效区间为 `[StackBegin, sp)`，可用容量为 `[sp, StackEnd)`。 |


现有地址偏移和地址寄存器运算使用 64 位宽度，`bp`、`sp`、`pc` 和数据指针采用统一的 64 位宿主地址表示。普通指令由分派循环推进 `pc`，显式控制转移由后续分支和调用指令完成。当前代码段搬迁会修补登记的 VM 符号地址及两类地址重定位字段；执行中的寄存器、活动栈及调用方保留指针的地址稳定性仍须由后续执行器设计保证。

每次调用拥有独立的帧，因此递归调用不会覆盖上一层调用的参数和局部变量。函数内的长期槽位建议使用 `bp + 固定偏移` 访问，短期的调用准备区可以使用 `sp` 相对寻址。

## 栈空间调整：建议约定

当前三种寄存器加法分派不检查 SP 容量；栈边界、地址有效性和活动帧约束由调用方保证。

以 `sp` 为目标的寄存器加法直接调整栈顶。下例中的 `rri` 按目标、左来源、右来源的顺序表示两个寄存器操作数和一个立即数操作数：

```text
add64rri sp, sp, 16     // 预留 16 字节
add64rri sp, sp, -16    // 回收 16 字节
```

建议写入 `sp` 时将来源立即数按有符号字节增量解释。正增量预留空间，负增量回收空间，零增量保持栈顶不变。预留的空间不初始化；回收的空间不再属于有效栈空间。

当前已实现 `Add64rrr`、`Add64rrm`、`Add64rri`、`Add64mrr`、`Add64mmi` 和 `Add64mmm` 的执行分派，结果按 64 位位模式回绕。`Add64mmi` 将内存值与立即数相加，`Add64mmm` 将两个内存值相加，二者写入内存目标；来源在目标写入前完整读取，允许未对齐和重叠访存。调用方负责保证栈范围、活动帧约束与地址的有效性。普通调用帧中的临时栈空间回收仍须遵守 [VM 调用约定](VM-Calling-Convention.md) 的布局。

栈空间增量由指令显式给出，普通加法按操作码位宽回绕。

函数返回时回收整个函数帧中的局部空间。函数内提前回收空间时，执行该调整的函数须保证已回收空间不再被使用。

建议按增量精确移动栈顶，不暗中取整。槽位间的对齐填充由布局方计入调整量，调用边界的对齐也由调用方保证。

## 函数调用与返回

调用族统一为 `Calli` 和 `Callm`，文本均为 `call`。`Calli` 保存完整 64 位函数地址，本镜像符号使用镜像基址重定位，外部符号使用动态导入重定位；符号 addend 为零。`Callm` 按寄存器基址加编码偏移计算指针槽地址，再按字节复制读取 64 位函数地址；槽位无需对齐，调用方须保证这八字节内存可读。

解释器从 `NativeSymbolAddresses` 建立 stub 地址 hash set。`Calli` 和 `Callm` 取得目标地址后共用调用逻辑：先检查目标是否位于有效代码段且按八字节对齐，满足时直接执行 Ink 调用；只有其他地址查询 stub 集合。命中时按 `void(Frame*)` 调用已注册 stub，stub 返回后继续 `NextPC`，不创建 Ink 保存区；未命中属于内部不变量失败，使用 `check`。调用方保证参数和返回槽满足各 stub 的既有契约；此集合不允许任意原始 C 函数指针自动进入宿主调用。

Ink 目标通过范围与对齐及栈保存区检查后，在 SP 处写入旧 BP 和返回 PC，再令 BP 为旧 SP、SP 前进 16 字节、PC 指向目标。普通 `Ret` 从保存区恢复 BP、PC，并将 SP 恢复到当前 BP；调用区由调用方回收。没有活动 Ink 调用时，`Ret` 结束本次执行。

每次执行读取 `config.def` 中的 `VMMaxRecursionDepth`，默认最多同时保留 8096 个 Ink 调用帧，可通过 `INK_VM_MAX_RECURSION_DEPTH` 覆盖。入口函数深度为零，Native stub 不增加深度；零限制禁止建立 Ink 调用帧，仍允许最外层返回和 Native 调用。到达限制时，下一次 Ink 调用通过 `REPORT_IF` 报告 `maximum recursion depth exceeded`；保存区容量不足时报告 `stack overflow`。两种情况均返回 `false`，保留失败调用前的寄存器和栈字节。

布局公式、参数及返回槽、可变参数预留区见 [VM 调用约定](VM-Calling-Convention.md)。当前尚无调用区自动生成或完整调用签名检查。

## 执行边界与失败：建议约定

`pc` 必须指向合法指令起点。解码需要验证操作码、操作数长度以及目标指令边界；普通指令成功后执行 `pc = NextPC`，调用保存的也是 `NextPC`。程序入口可以使用专用的初始调用帧，最外层返回结束执行，不将任意地址当作退出哨兵。

当前 `execute()` 和 `dispatch()` 通过 `bool` 返回执行是否成功；无效入口、CALL 保存区容量不足、超出最大递归深度和已知但尚未实现执行的 opcode 通过诊断引擎报告 `VMExecutionFailed`。`Add64rrr`、`Add64rrm`、`Add64rri` 写 SP 时不检查栈容量；函数入口的栈峰值检查和动态栈分配检查尚未实现，见 [TODO](todo.md)。分派内部的 PC 范围、编码完整性、保留位、寄存器合法性、调用目标及 CALL/RET 帧结构和保存的返回状态使用 `check` 契约；关闭断言时仍须由调用方保证这些前置条件。普通访存有效性和地址运算约束同样由调用方保证。程序退出值和完整执行错误状态的对外接口仍待设计。

可执行镜像结构验证与执行验证分开处理。现有 `ExecutableFileValidator` 检查入口在镜像内以及统一导入、地址重定位和导出符号的结构，不解码指令。镜像固定使用小端序，不保存字节序配置；也不保存段表，导出符号只记录名称及镜像内偏移。代码范围识别、指令边界建立及数据权限策略仍待确定。指令编码、镜像布局与发射已实现，其他 opcode 的解码和独立模块 validator 仍待实现。现有镜像结构校验不提供运行时调用约定或访存验证；后续执行器仍须补全指令边界、活动帧、地址和权限检查。

## 后续讨论

按 [VM 调用约定](VM-Calling-Convention.md) 自动生成调用区布局和通用宿主 ABI adapter 尚未实现。`opcode.def` 中已有形式的操作数编码以 [VM 指令编码格式](VM-Instruction-Format.md) 为准；当前已支持 `Calli`、`Callm`、恢复调用帧的 `Ret` 与分支控制流，其他指令执行仍需补全。
